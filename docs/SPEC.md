# Nazgarr — Functional and architectural spec (v1)

A document consolidated from a user's stream of ideas, reorganized and grounded by comparing it against four related local projects. Not an open brainstorm: wherever something is explicitly undecided, it's flagged as such at the bottom (section 15).

**Name** (renamed 2026-09-29, user decision): project name **"Nazgarr"**, repo/technical name **`nazgarr`**. It was "The Media Gauntlet*rr" / `gauntletarr`, and the rename carries the data along (`gauntletarr.db` is renamed at startup, `nazgarr/core/db.py`). It's *arr style (like Bazarr/Cleanuparr/Prowlarr) without actually depending on Sonarr/Radarr, the same stylistic "wink" Auditorr already does. "Nazg" is a fantasy word for "ring" and the icon is a plain golden ring: a light fantasy flavour is fine in the UI, but no direct references to the source works or their marks, and none in the README. The **Media Stones** theme below comes from the old name and stays only as internal naming of domains/phases for now; a re-theme around the new name is to be evaluated (it isn't visible in the UI today).

## Theme: the Media Stones

Six "stones," one per main functional domain — used as a reading key to organize the spec and as the basis for the visual identity (icon/color per module in dashboard and sidebar), not as a rename of the underlying technical concepts (the code/API keeps ordinary descriptive names: `media_item`, `TorrentClientAdapter`, etc. — the Stones are a branding layer on top, not a replacement).

| Stone | Color | Domain | Section |
|---|---|---|---|
| **Stone of Bond** | Blue | Disk/hardlink model, unified per-file state (orphaned/ignored) | §3-4 |
| **Stone of Control** | Purple | Multi-client torrent adapters, presence/seeding state | §5 |
| **Stone of Knowledge** | Yellow | Content identification (TMDB), poster cache | §6 |
| **Stone of Reintegration** | Red | Matching and reseeding engine (repairs broken links) | §6, 8 |
| **Stone of Time** | Green | Scheduling, run history, dashboard trends over time | §8, 10 |
| **Stone of Genesis** | Orange | Upload — gives content "new life" by publishing it to a tracker | §9 |

"Wearing the gauntlet" = having all six Stones configured and active (disks mapped, clients connected, resolver working, matching engine active, scheduler configured, upload ready) — also useful as a metaphor for a future onboarding/setup wizard in the UI: a six-item checklist before the system is "complete."

## 0. Provenance — where this project comes from

This doesn't start from scratch. It synthesizes:

- **`ratio-guardian`** (its own `docs/SPEC.md`, a separate project): the most mature architectural analysis and the closest to this scope — a disk/hardlink model with no Unraid/FUSE dependency, a TMDB matching engine with explicit confidence, a reseeding engine with forced recheck, and — decided in that project's most recent session — a second "Upload" mode inspired by Upload-Assistant. Nazgarr **inherits ratio-guardian's entire data architecture and matching/reseeding engine**, which should be read for the verified implementation details (the real shape of the UNIT3D API, already-fixed known bugs like the season pack size comparison, mediainfo edge cases). This document doesn't repeat those details where they haven't changed, it references them.
- **Auditorr**: reference for the visualization experience — library tree view, per-file state (presence/hardlink/seeding), dashboard with a "library health" gauge, reverse hardlink lookup from the torrent side.
- **Upload-Assistant**: domain reference for the upload flow (mediainfo, screenshots, description, dupe-check, ~90 supported trackers). **In development freeze** as declared by the project itself — to be treated as a domain reference to reimplement against our own contracts, never as a live dependency.
- **smartmediareseed**: reference for verifying file↔torrent identity via **piece hashes** (BEP3) against the hash declared in the `.torrent` — a stronger confidence signal than mediainfo Unique ID alone (which doesn't distinguish different audio tracks on otherwise-identical video). To be integrated as an additional signal in the matching engine (section 6), never as a substitute for a real recheck.

## 1. Vision and problem

The user manages a media library (movies/shows) and one or more torrent seeding folders, often on separate physical disks with no RAID/FUSE. Everyday use accumulates drift:

- files moved/renamed in the library that break the hardlink and therefore seeding, without the user noticing (ratio-guardian's core problem);
- files present in the torrent folder that the torrent client no longer tracks (removed from the client, client reinstalled, a migration never completed);
- files seeding that were never organized/linked into the actual media library;
- downloaded/organized files that were never correctly identified (no TMDB match), and are therefore invisible to any matching logic.

Nazgarr has to give **a single, coherent view of every file's state**, on both sides (media and torrent) and on the torrent client itself, plus the tools to fix every kind of drift: reseeding, manual linking, uploading new content.

## 2. Genericity requirements (binding, inherited from ratio-guardian §2)

- **Must not assume Unraid/FUSE.** N separate physical disks, each potentially holding part of the library, with no unifying filesystem.
- **Must not assume Sonarr/Radarr.** Optional integration as an additional media resolver adapter, never a dependency.
- **Adapter architecture for trackers, torrent clients and media resolvers**, to allow future extension without rewrites (detail in section 5).
- Distribution: Docker container, web UI for configuration.
- **Designed for public/open source release** (an explicit decision, unlike the source tools which are for personal use): implies example config with no personal data, no hardcoded secrets, clean `.env.example`/`config.example.yaml`, a LICENSE, and care not to assume the original user's specific setup (paths, trackers, disk names) in any default.

## 3. The two directions of the problem: orphaned and ignored

The central point of the original request, distinct from (and complementary to) the "media→torrent" model ratio-guardian already covers. **Both scan directions** need to be maintained, on the same hardlink graph:

### Media → torrent direction (already covered by ratio-guardian's engine)

Files in the media library **without** a valid hardlink to the disk's torrent folder → candidates for the matching/reseeding engine (section 6). This is the "I moved/renamed the file and broke seeding" case.

### Torrent → client/media direction (new requirement for Nazgarr)

For every file in a disk's torrent folder:

- **Orphaned file**: present on the filesystem (torrent folder) but **not tracked by any configured torrent client** (no torrent in the client whose resolved path points to that file). Typically: a file left behind after removal from the client, a migration that was never finished, a reconfigured client. The natural action: the same reseeding engine as ratio-guardian, but triggered from the torrent side — search the configured trackers for a match for that file (size + mediainfo + piece hash, section 6), and if the match reaches maximum confidence (100%, not the 0.95 threshold used for the media→torrent case — see note below) **download the `.torrent` from the tracker and add it to the client pointing at the file that's already there**, with no need to recreate the hardlink (the file is already in place).
- **Ignored file**: present on the filesystem (torrent folder) and correctly tracked by the client, but **with no hardlink into any enabled `MediaPath`**. It's a seeding file "orphaned from the library": technically healthy, but invisible to the user's media organization. Action: flag only in the UI (never automatic) — the user decides whether it's worth organizing (manual hardlink into a MediaPath) or leaving it as-is (e.g. cross-seeded content that isn't theirs).

**"Tracked by a client"** means the torrent was present at the latest complete, successful listing of that client. A torrent removed from the client leaves the index at the next scan, and its file becomes an orphan again. A torrent Nazgarr registered on its own after the listing was asked for (an upload, a reseed or a Radarr/Sonarr import, `nazgarr/library/seed_refresh.py`) is not in that listing, so it is kept with its files until the next one (audit 2026-10-18): before, a run whose listing started just before the add removed it, and the freshly seeded file was an orphan again until the run after, which searched it on the trackers. A file whose torrents are all stopped (paused) in the client stays `seeding` in the state model, with a separate `stopped` flag in the UI. An execution that reached seeding and whose torrent was then removed from the client is shown as "removed from client", and it no longer blocks a new review for that torrent.

**Library ↔ torrent link by inode:** a library file is hardlinked (and seeding, if a client tracks the torrent side) when **any** torrent-side file shares its inode on the same disk. It does not depend only on the single `seed_file.media_file_id` the scanner writes. The same inode reachable from two library paths (e.g. a double import by Sonarr/Radarr) is therefore seeding on both paths, and is never searched as an orphan (`nazgarr/library/hardlinks.py`). Duplicates come in two kinds: `copy` (same content on different inodes, wasting space) and `hardlink` (same inode under several library paths: no extra space, but the content appears twice and one path can be deleted without touching the seed).

**Note on the threshold for torrent-side orphans**: the risk here differs from what's discussed in ratio-guardian §9 (a false positive that leads to seeding the wrong data). Adding a torrent that's already present locally based on a wrong match is still risky (it associates the file with a torrent that isn't a match; the client rechecks it and, worst case, fails — less severe than a false hardlink, but not harmless). So treat it with the **same severity**: a high, configurable threshold, and below it, the manual review queue, exactly as for the media→torrent case — never a bypass "because the file already exists."

### Unified per-file state

Every file (on either side) must expose a composite state, inspired by ratio-guardian's Library page (§12) but extended:

| State | Meaning |
|---|---|
| `seeding` | Valid hardlink + tracked by the client, actively seeding |
| `orphan_media` | In the media library, no valid hardlink (reseeding candidate — media→torrent direction) |
| `orphan_torrent` | In the torrent folder, not tracked by any client (reseeding candidate — torrent→client direction) |
| `ignored` | In the torrent folder, tracked by the client, no hardlink into the media library |
| `unmatched` | No TMDB match resolved (unparsable filename, or no tracker candidate), regardless of side |
| `pending_review` | A match was found but below the confidence threshold, in the manual review queue |

A media file counts as seeding only through a torrent a client tracks. A hardlink in the torrent folder that no client follows doesn't count: for example, a file downloaded by hand into the torrent folder and imported by Radarr is still searched as `orphan_media`. **Cross-seeds** (user decision, 2026-10-02, on by default, setting `cross_seed_search`): for each tracker, the media→torrent matching searches the files that don't seed on *that* tracker, so a file seeding on tracker A is also searched on tracker B. Reviews are kept per file and tracker, so a file can have one proposal on each tracker. A candidate whose info hash is already in a client is dropped. When the destination of a hardlink already exists with the same inode (the same release, under the same name, seeding for another tracker), execution reuses it instead of failing. A different file at that path is still an error and is never overwritten. **Symbolic links on the way are never followed** (audit 2026-10-18, `nazgarr/library/hardlinks.py`): `check_link` looks at the destination as written, not resolved (the reseed executor and the upload flow both pass it unresolved; the executor used to resolve it first, so for reseeds the rule did not apply), so a symbolic link in its place is `target_exists` wherever it points, even outside the root (the symbolic links are checked before the scope resolution) (before, a dangling one made the hardlink at the place it pointed to, and one pointing at an existing hardlink was "reused" as a cross-seed), and a symbolic link for a folder above it is out of scope, wherever it points. Hardlinks are then created and removed through the folders opened one by one with `O_NOFOLLOW` (`openat`/`linkat`/`unlinkat`): a folder turned into a symbolic link between the check and the link (a database commit, for the executor), or before a cleanup, makes the operation fail instead of placing or removing a file elsewhere. A cleanup removes only the file it created (audit 2026-10-18): `create_links` records the device and inode of each new link, read in the opened folder right after linking, and the removal compares them in the same opened folder (`fstatat`, then `unlinkat` on the same descriptor), so another file put under that name since, or swapped in after the caller's own check, stays and is logged. A path with no recorded identity is removed only if it is still a regular file. The same holds when a new seed is registered right after its recheck (`nazgarr/library/seed_refresh.py`, which looks for the hardlinks where the executor put them, by the client's content layout): a path is read as written, and a symbolic link in place of the hardlink, or for a folder below the configured one, is never registered as a seeding file nor used to pick the layout (audit 2026-10-18: one pointing at the library file had its inode and passed for its hardlink). The reseed executor still resolves the destination before `check_link`, so a symbolic link already sitting at a reseed's destination is not caught there yet. The review queue marks these proposals as "Cross-seed · seeding on X" (`nazgarr/library/seeding.py`).

**Packs and singles on the same tracker** (user decisions, 2026-10-08). A torrent with more than one video is a *pack* (a season or a series); one with a single video, extras included, is a *single*. Only episodes have formats: a movie with video extras is never a pack.
- **Off (default):** an episode gets one proposal per tracker, and a plausible pack always wins over the singles (usually, once the pack is out, singles are no longer uploaded). A pack queued or approved for another episode keeps this episode's single out of the queue while it can still serve it ("One evaluation per pack per run", section 6, 2026-10-22), and proposing a pack takes the singles of its other episodes out of it (system rejection). A pack the user rejected counts as rejected for every episode in it, so it never comes back through another episode.
- **On** (setting `reseed_pack_and_singles`): an episode that seeds nowhere on that tracker gets one proposal per format, and an episode seeding there in one format is searched there in the other one only (the history's single torrent no longer stops the catalog search for the pack). A proposal closes once the episode seeds there in its own format.
- **The queue:** the single episodes of a season on one tracker are one row (series, season, how many, which episodes, the confidence range) with Approve all and Reject all (confirmed), and each episode underneath. A proposal for the format missing on its own tracker is marked "Second format".

## 4. Data architecture (inherits ratio-guardian §3-4, §13 — extended here)

Disk/library model from ratio-guardian: a **Disk** entity (physical root, cached `st_dev` to detect remounts), its **folders** (`disk_folder`, user decision 2026-10-03), paths always relative to the disk (never absolute), two-level validation (scoped file browser in the UI + `st_dev` comparison at runtime before every hardlink). See ratio-guardian SPEC.md §3 for the full reasoning — not repeated here. Full table-by-table DB schema: `docs/schema.sql`.

### Media and seeding folders (user decision, 2026-10-03)

A disk has **any number of media folders and seeding folders** (`disk_folder`, `nazgarr/library/disk_folders.py`). Examples: `movies/` and `tv/` side by side with no common parent, or `torrents/` plus a cross-seed folder. They replace the single `disk.media_rel_path`/`torrents_rel_path`, which are moved into `disk_folder` at startup and cleared (`nazgarr/core/db.py::migrate_disk_folders`).

- **No type per folder:** movie or TV is still detected per file. This matches the earlier decision that removed the typed `media_path`.
- **Rules for a folder:**
  - it is inside the disk, exists, and is not the disk root;
  - it is on the disk's filesystem, because hardlinks cannot cross filesystems. A folder mounted from another filesystem is refused with a hint to add it as a disk of its own;
  - it is never equal to, inside, or containing another folder of the disk, of either kind;
  - it is never inside the watched folder, nor that folder itself; containing it is fine (a dedicated subfolder such as `torrents/watch`). The same holds for the folders for new hardlinks and for uploads (audit 2026-10-18: before, only choosing the watched folder was checked, so an upload folder set inside it later became a release, and approving it removed the files earlier uploads seeded from).
- **Removing a folder** touches nothing on disk. Its files leave the library at the next scan.
- **The scan** reads every folder. A folder that cannot be read (an unmounted share) keeps its files current: their `last_scan_id` is carried forward. Without this, files would disappear with the share. A file gone from a readable folder still disappears as before.
- **Defaults:** new hardlinks and uploads go to their own folder if set, otherwise to the first seeding folder. The "already seeding" search covers every seeding folder.
- **Disk test** (user report, 2026-10-03): "Test disk" on the card (`POST /api/disks/{id}/verify`, `nazgarr/library/disk_folders.py::test_disk`) runs these checks:
  - every folder exists and is on the disk's filesystem;
  - a test hardlink goes from the first seeding folder to every other folder. The test file is empty, hidden and removed right away. If the disk has a single folder, the link stays inside that folder.
  - only the files the test created are removed (audit 2026-10-18): a link that fails because the name is taken leaves that file alone, two stored spellings of the same folder (`torrents` and `torrents/`, from an old migration) are recognised as one folder instead of ending in a 500, every folder goes through `resolve_scoped` (one stored outside the disk is reported missing, never written), and the link goes through `nazgarr/library/hardlinks.py` like every other.

  A changed `st_dev` alone is only a warning: on FUSE (Unraid `/mnt/user`) it changes at every remount, and it never proved hardlinks work. The stored value is updated when the link test passes.
- **API:** `GET /api/disks` lists `folders`, `media_folders` and `seeding_folders`. `POST /api/disks/{id}/folders` and `DELETE /api/disks/{id}/folders/{folder_id}` manage them. `media_rel_path`/`torrents_rel_path` remain as deprecated fields: the first folder in responses, and a single-folder replacement in a PATCH.
- **UI:** Configuration › Storage has one card per disk, like torrent clients and trackers. Each card lists its seeding and media folders, each with add and remove, and then the folders for new hardlinks, uploads and releases.

### Two supported layouts: per-disk mounts or a single TrashGuide-style mount

Where a disk can be (user decision, 2026-10-05, replacing a required `disk_scan_root`): inside a container, the data folders the user mounted. `nazgarr/core/mounts.py` reads `/proc/self/mountinfo` (only when `NAZGARR_CONTAINER=1`, set by the Dockerfile, or `/.dockerenv` exists), drops system filesystems and folders, mounted files (`/etc/hosts`) and Nazgarr's own config and data folders, and what is left is the scope: decided by the Docker template, not by a setting a browser could change, so it stays as safe as a static root. `disk_scan_root` in `config.yaml` is now optional: when set it is the scope (installs from before keep working), and mounts outside it are reported; outside a container `nazgarr init` writes it, and without it the scope is `/data`. Storage lists the detected mounts with their filesystem, proposes the ones that are not a disk yet ("Add as a disk") and refuses a disk inside another one (`disk_root_nested`). **Nazgarr's own folders are never inside a disk**, in every mode (audit 2026-10-18, `Scope.app_folder_in`): a disk root that is or contains the config folder (`config.yaml`, `secret.key`) or the data folder (the database), or that sits inside the data folder, is refused (`disk_root_contains_app_data`) and never proposed. Before, with a broad `disk_scan_root` (the home folder, for a pipx install) those folders could be browsed and hashed into a torrent. A root inside the config folder stays possible, since that folder may be any working folder. With a configured root, hidden first-level folders (`~/.config`, `~/.local`) are not proposed either; they can still be typed. Two layouts get a warning, because Nazgarr can see them and the user cannot:

- **`split_mounts`**: two mounts of the same filesystem (same device), e.g. `/data/media` and `/data/torrents` mounted separately, also from the Unraid share. The kernel refuses a hardlink between two different mounts even on the same disk: mount the common folder instead.
- **`share_and_disks`**: the Unraid user share (`fuse.shfs`) mounted next to single disks: the same files would be seen twice. The share alone is fine: shfs creates a hardlink on the same physical disk as its source.

The two usual layouts:

- **Single mount (TrashGuide convention)**: mount one combined torrents+media folder at `/data` — the same host path shared with the download client and media manager, which is what makes hardlinks between them work. In this layout there's a single Disk, registered with `root_path` equal to the mount itself.
- **Per-disk mounts (classic Unraid layout)**: each physical disk is bind-mounted directly (`/mnt/disk1`, `/mnt/disk2`, ...), and each shows up as its own registerable Disk. No common parent and no `disk_scan_root` are needed any more.

Either way, the runtime `st_dev` check before every hardlink (§3, `create_disk`/`verify_disk`) is the actual safety net: even inside a single combined mount, individual files are tracked with their own `st_dev` (not just one value per Disk row) — see "The two FKs" below — so a hardlink attempted across two files that don't really share a device fails with an explicit error rather than silently corrupting anything, whichever layout is in use.

### Why ratio-guardian's model isn't enough as-is

Ratio-guardian merges logical identity and physical file into a single row (`media_item` has both `tmdb_id` and `file_path`/`inode`) and **has no table at all for the torrent client inventory** — it checks "is this already seeding" with a live filesystem check (`find -samefile`) plus a client query only at execution time. That works for a single client with no need to see cross-seeding, but it doesn't hold up against Nazgarr's requirements (multi-client, a grid view grouped by content, explicit visibility of every cross-seed claimant — §3, §5, §7). Auditorr's model was also analyzed, as a negative reference: it keeps everything in JSON blobs recomputed on every run and, for cross-seeding, merges every claimant on the same inode down to just "the healthiest one" (`audit.py::_walk_directory`, lines 106-124) — an efficient choice, but one that **loses information**, exactly the opposite of what's needed here.

### The entities (physical separated from logical, as discussed)

```
media_item            -- resolved logical identity: tmdb_id, season, episode, poster
  media_file           -- physical, media side: disk_id, relative_path, size, st_dev/inode
                        --   "as of last scan", media_item_id (FK)

seed_file              -- physical, torrent side: disk_id, relative_path, size, st_dev/inode
                        --   "as of last scan", media_file_id (FK, nullable — see below)
                        --   one row per hardlink sibling: 3-way cross-seed = 3 rows

torrent_client          -- config (already exists)
  client_torrent          -- ONE torrent for ONE client instance: info_hash, name, save_path,
                          --   category, state, tracker_url — UNIQUE(torrent_client_id, info_hash)
    client_torrent_file     -- ONE file inside a client_torrent: path_in_torrent, size,
                            --   seed_file_id (FK, nullable)
```

`media_item` is separate from `media_file` (unlike ratio-guardian, where they're the same row) because the grid view (§7) needs to group several physical files under one poster — a common case for a season with multiple episodes, or content with several versions/qualities in the library.

### The two FKs, and why they're written differently

- **`seed_file.media_file_id`** (the inode link, cross-seed): **never computed at runtime with a live join** on `(disk_id, st_dev, inode)` — on a large library that would be recomputed every time the tree/grid view loads. Instead it is:
  1. computed **once per scan**, in memory, during the same `os.walk` already needed to read `st_dev`/`inode`/`nlink` (the same technique Auditorr uses — a dict kept for the duration of the scan — but here **without discarding the "losing" claimants**: every sibling stays a row);
  2. written with a **bulk upsert at the end of the scan** (batch insert/update, never a per-file query);
  3. tagged with `last_scan_id` (a FK to `run_log`) — a `seed_file` not seen again in a later scan isn't deleted right away (the review queue still needs to be able to show it as "gone"), but its `media_file_id` stops being trusted for current-state computations until it's reconfirmed. This avoids the concrete risk of inodes being reassigned by the filesystem between one scan and the next (the same problem already flagged as open in ratio-guardian §17 — made explicit and handled here).
- **`client_torrent_file.seed_file_id`** (the path link, not inode-based): resolved by comparing `client_torrent.save_path + path_in_torrent` against `disk.root_path + seed_file.relative_path` — doesn't suffer from reassignment (a path doesn't get "reused" for a different file the way an inode number does), so it's more stable across scans, though still reverified on every scan for consistency.

On read, every state query (§3) and every dashboard count (§10) is an indexed JOIN on these FKs — never a computation on `st_dev`/`inode` at runtime, which stay **write-only** columns for the scan process.

### Other extensions

- **Poster cache**: `media_item.tmdb_poster_path` (relative TMDB path) + a local cache of the downloaded images (filesystem, not a DB blob — a predictable path like `data/posters/{tmdb_id}.jpg`, downloaded once and reused). Needed for the grid view (§7).
- Static YAML (`data_dir`, optional `disk_scan_root`) / dynamic DB (disks, media paths, trackers, clients, thresholds) config split, as in ratio-guardian §4; in a container the disk scope comes from the mounts (above).

Matching/reseeding entities (`candidate`, `match_review`, `seed_job`) and the new upload entities (§9) stay as in ratio-guardian, adapted to reference `media_item`/`media_file` instead of ratio-guardian's merged row — full detail in `docs/schema.sql`. One real gap found while building Fase 4: `candidate.media_item_id` alone isn't enough to know *which physical file* a match applies to when a `media_item` has more than one `media_file` (different quality versions of the same content) — never an issue in ratio-guardian, where a media_item *was* the physical file. Fixed by adding `match_review.media_file_id`/`match_review.seed_file_id` (whichever applies to the candidate's `direction`), so the decision — not just the search result — carries the physical file it's about.

### Deleting a tracker, a disk or a client (audit 2026-10-18)

Every foreign key says what a delete does, so deleting a configured tracker, disk or client never fails on what depends on it. Before, a tracker that had found a single candidate, or a disk with one successful reseed, could no longer be deleted (a 500, `FOREIGN KEY constraint failed`). Only database rows change: nothing on disk or in a torrent client.

- **Tracker**: its candidates go with it, with their files, reviews and executions (`seed_job`), and so do its match attempts, upload targets and upload profile. Disabling a tracker (`enabled = false`) keeps all of that.
- **Disk**: its folders, its media and seed files, their reviews, match attempts and executions go with it. An execution always has exactly one source file, like a review, so it leaves with it instead of staying with neither. Candidates belong to the tracker and stay, without their local file. Upload jobs and not-imported rows stay, without the reference.
- **Client**: its indexed torrents go; an execution only loses its `result_client_torrent_id`.

**User decision, 2026-10-18**: deleting a tracker or a disk that has been used takes its history with it, as above (`ON DELETE CASCADE`): a tracker's candidates and their reviews, executions, match attempts, upload targets and upload profile; a disk's folders, media and seed file records and their reviews, match attempts and executions. Disabling a tracker (`enabled = false`) remains the way to keep all of that. Since the delete cannot be undone, it is confirmed with the counts of what goes: `GET /api/trackers/{id}/delete-preview` and `GET /api/disks/{id}/delete-preview` (read only) count it, the delete dialogs in Settings show those counts (only the non-zero ones) and say that nothing changes on the disk, on the tracker or in the torrent clients (a reseed that is seeding stays in its client: only its record goes; a disk's upload jobs stay in the history without the disk), and `nazgarr tracker rm` / `nazgarr disk rm` print the same before asking (`--yes` in a script). The preview also says when the delete would be refused (`busy`, below): the dialog says why and keeps Delete off, and the CLI stops before asking.

**Done** (audit 2026-10-18, wave 2): before the cascades, a tracker or a disk that had been used could not be deleted at all, so neither could be deleted while one of its executions or uploads was running. With the cascades the delete could remove the `seed_job` the executor is working on, and its next commit (`hardlink_created_at`, `torrent_added_at`) would find no row, leaving a hardlink or a client torrent with no record. So `DELETE /api/disks/{id}` refuses with `disk_busy` (`work`: `reseed` or `upload`) while a `seed_job` of its files is `in_progress` or an `upload_job` of the disk is in a worker state (identifying, analyzing, queued, running), and a constraint that still fails on the commit is a coded 409 (`disk_delete_conflict`) instead of a 500.

`DELETE /api/trackers/{id}` does it (audit 2026-10-18): `409 tracker_busy` while an execution of one of its candidates is `in_progress`, or an upload to it is in a worker state (identifying, analyzing, queued, running) or one of its targets is being sent (preparing, uploading, seeding), and also (audit 2026-10-18) while one of its targets holds a torrent stopped in an enabled client waiting for its recheck (`seed_recheck_pending`, a reseed of the upload flow or a Retry seeding): the reconcile follows only that row to start the torrent, so the cascade left it stopped for good, the same reason deleting such an upload is refused (`upload_seed_recheck_pending`). With its client disabled or deleted the reconcile does not follow it anyway, so the delete goes through. A queued or scheduled upload is cancelled, or a stuck execution deleted, first. A row that still refers to the tracker without a delete action (a database the migrations have not rebuilt) gives `409 tracker_in_use` instead of a 500. The tracker's request fields are bounded too: `rate_limit_per_min` from 0 (the default, 30) to 600, since a negative value made every call to that tracker fail with an `IndexError` in the rate limiter. A tracker saved before that bound is normalized once by a migration step (audit 2026-10-18): below 1 becomes 30, above 600 becomes 600. Without it the limiter read such a row as 1 request a minute, and the edit form resent the stored value, refused with a 422. So are a Radarr/Sonarr instance's `timeout_seconds` (1 to 300; a negative one reached httpx as an invalid timeout; a row saved before that bound gets the default 15, or 300 when it was longer, and the API shows that value, so the edit form never resends one it refuses) and the dashboard history's `limit` (1 to 1000) and `days` (1 to 3650): a negative `limit` returned every run and a huge `days` was a 500.

Every foreign key column leads an index (`tests/test_consistency.py` checks it), except the references to `run_log`, whose rows are never deleted. Without them each deleted row scanned its child tables: 53 s for a disk with 3000 files against 200k `candidate_file` rows, holding the write lock. Existing databases get the new delete actions from migration step 10. It rebuilds `candidate`, `seed_job` and `upload_job` as `docs/schema.sql` has them, which also gives `upload_job.split_from_id` the foreign key it lacked where `migrate_schema` had added the column (databases from before 0.9.4). A split pack could be deleted there while its episodes kept its id: step 10 clears those values, as `ON DELETE SET NULL` would have done. A new foreign key with another action that finds such values stops the step and names the table and the column. A step that rebuilds a table runs inside `db.rebuilding_tables`: foreign keys off outside the transaction, one transaction, foreign keys back on after the commit. An interrupted start then leaves nothing half done, and the pooled connections never lose foreign key enforcement.

### Database updates at startup: backup first, recovery mode on failure (user request, 2026-10-22)

The user asked for "an automatic backup of the DB before the migration, so the user can be told about an error in the migration and where to recover the backup from". At every start `nazgarr/core/migrations.py::upgrade` brings the database to the current version: the numbered one-off steps (tracked with `PRAGMA user_version`, the version moves only after every pending step succeeded), the new columns (`migrate_schema`), `docs/schema.sql` (`apply_schema`) and the encryption of secrets left in clear. Before that, `nazgarr/core/db_startup.py::prepare` runs:

- **The secret key first.** A missing or malformed `APP_SECRET_KEY` fails the start before anything else, as it did before (`crypto.check_key`): it is a configuration error, and restoring a backup would only throw data away.
- **What will change** (`nazgarr/core/db_backup.py::pending_changes`, read-only, on its own `sqlite3` connection): numbered steps pending (`user_version` below the latest), or tables, indexes or model columns missing. A new or empty database, one with nothing pending and one newer than this Nazgarr (a downgrade) get no backup. A database another process holds (`SQLITE_BUSY` after the 30 s busy timeout) is reported as `database_locked`, never as damaged, and is not touched.
- **The backup**, only when something will change: SQLite's online backup API (consistent with what is still in the `-wal`) into `<data_dir>/backups/pre-migration-v<from>-to-v<latest>-<app version>-<UTC time>.db`, switched to a single file (journal mode DELETE), created `0600` before anything is written into it (encrypted secrets and personal data inside, the folder is `0700`), fsynced, renamed from a `.partial` name, then reopened read-only and checked (`PRAGMA quick_check` is `ok`, it has tables, its `user_version` is the starting one). The copy first opens a read transaction under the busy timeout: CPython's `backup()` retries `SQLITE_BUSY` forever, and a locked database used to hang the start. Free space is checked first: the database plus its `-wal` plus 10% and 32 MiB. The newest 3 such files are kept (`NAZGARR_MIGRATION_BACKUPS_KEEP`, at least 1); no other file of that folder is ever removed, the backup just taken and the one a failed attempt points to are never pruned, and neither is any backup written after the one just taken (a clock that was ahead, on a NAS or a Pi without RTC before NTP, can give old backups later names). The log says `Backup before the database update: <path>`, and after a successful update the backup is recorded in the internal setting `migration_backup_last` (`settings_registry.MANAGED_KEYS`), shown in Settings › Application with its folder (`GET /api/system/info`: `migration_backup`, `backups_dir`, `backups_keep`).
- **No backup, no update.** When the backup cannot be made (no space, an I/O error, a copy that fails its check) the database is not touched. `NAZGARR_SKIP_MIGRATION_BACKUP=1` lets an operator update without it (a warning in the log). A database SQLite cannot read at all (damaged, not a database) cannot be copied either: the reason is then `database_unreadable`, and the page points to restoring a backup instead of freeing space (before, the same file was a crash loop).
- **Recovery mode instead of a crash loop.** Before, a failing step escaped the lifespan, supervisord restarted the process forever and the user saw only a traceback. Now `upgrade` raises `MigrationFailed` with the step number and name (`None` and the function name for the per-start steps), and when that or the backup fails the process stays up without the scheduler, the upload worker, the plugin switches or any route that touches the database. It writes `<data_dir>/migration-status.json` (`0600`: status `migration_failed` or `backup_failed`, from/to versions, step number and name, the error class and first line without SQL or parameters and with link secrets redacted, the backup path, the UTC time, a fingerprint of the database file) and logs an ERROR with the same, the restore instructions and the full traceback. `nazgarr/web/recovery.py` answers every request before routing, with or without a body (in this mode the body limit middleware does not ask for credentials, there is no database to check them against): `GET /api/health` with 503 (the container's HEALTHCHECK turns unhealthy), every other `/api/*` with 503 and a code of its own, `database_update_failed` (`step`, `step_name`, `backup`), `database_backup_failed` (`reason`) or `database_in_use`, everything else with a self-contained page in Italian or English (Accept-Language), no script, no login (the database may be half updated): the step, the error class only (the message and trace stay in the log), the backup's name and folder (inside a container, a note that `/app/config` is the mounted folder), and how to restore it. On the next start that updates the database successfully, `migration-status.json` is removed.
- **A restart does not replace the good backup** (review of 2026-10-22). Before calling `upgrade`, `migration-status.json` is written (fsynced, then renamed) with status `in_progress`, the backup, the from/to versions and the starting `user_version`. A later start that finds `in_progress` (the process died mid-update: out of memory, the SIGKILL after `docker stop`'s timeout, a power cut) or `migration_failed`, with the database still at that starting version (`user_version` moves only at the end), treats it as the same update whatever the file's fingerprint: it reuses the backup of the first attempt and never copies the half-updated database under a `pre-migration` name, which would have pushed the real one out of the kept ones after a few restarts. If the database changed since the previous attempt (fingerprint: size, mtime, inode, `-wal` size; for example restored by hand and used for days with the previous version), it is also copied as `pre-retry-v<from>-to-v<latest>-...db`, with its own retention, and the page and log mention it as the one to restore only if Nazgarr was used in between. A later backup failure (database locked or unreadable, a `pre-retry` copy that could not be made when no other copy exists) keeps the record of the interrupted update (`interrupted_update`), so the start after it still recognises it.
- **Restoring** (`nazgarr db backups`, `nazgarr db restore <file>`, local commands like `reset-password`): the restore checks the backup, keeps the current database as `nazgarr.db.before-restore` (with the time if one is already there), byte for byte with its `-wal` next to it (`nazgarr.db.before-restore-wal`, SQLite reopens them together): nobody writes while the restore holds the lock, and a file SQLite cannot read is kept as it is, removes `-wal` and `-shm` (a stale `-wal` would be replayed on top of the backup), replaces the file with an atomic rename, and removes `migration-status.json`, so the next start is a new update with its own backup (by hand, the user deletes it too). It refuses while a Nazgarr process holds `<data_dir>/nazgarr.lock` (an OS lock, `flock`, released by the kernel when the process ends, `nazgarr/core/instance_lock.py`). The server holds it while it uses the database and lets it go in recovery mode, so in Docker the restore works with `docker exec` while the recovery page is up. The lock works both ways: a server that starts while a restore (or another Nazgarr) holds it waits 10 seconds, then stays in recovery mode (`database_in_use`) without opening the database or writing `migration-status.json`. The backup's name says its schema version: the user then starts the version they had before, or reports the issue.

## 5. Torrent clients: multi-client support from v1

An explicit requirement, unlike ratio-guardian (which starts with a single qBittorrent adapter and is generically extensible but with no immediate commitment to other clients). Priority:

1. **qBittorrent** — via `qbittorrent-api`, first adapter, implemented (`nazgarr/adapters/torrent_client/qbittorrent.py`). **Validated against a real instance** (deployed on Unraid, `POST /api/torrent-clients/{id}/test` confirmed a working connection) — tests still use a mocked client, the real-instance check was manual.
2. **qui** (multi-instance manager for qBittorrent, `nazgarr/adapters/torrent_client/qui.py`) — the Phase 2 pragmatic assumption above (treat it as plain qBittorrent pointed elsewhere) turned out to be **wrong**, confirmed against qui's own OpenAPI spec (github.com/autobrr/qui) and against Auditorr's own working qui integration (`sources/_qui.py`), not just deduced: qui exposes its own aggregation API (`X-API-Key` header, paths under `/api/instances/{id}/...`), not the qBittorrent WebUI API `qbittorrent-api` expects. A deployment manages several qBittorrent instances behind one host+key; `add_torrent` has to target one specific instance deterministically, so one `TorrentClient` row maps to exactly one qui-managed instance (`torrent_client.qui_instance_id`), never chosen at runtime like Auditorr's read-only aggregation across "eligible" instances does. No endpoint exists to read a single torrent's status by hash (confirmed absent from both the OpenAPI spec and Auditorr's implementation) — `get_torrent_status()` therefore does a full paginated scan per call, documented as a known inefficiency in the adapter's own docstring rather than hidden. Still unverified against a real qui instance (built and tested against the real, published API contract and mocks only) — same category of open item as qBittorrent's own real-instance check once was.
3. **Deluge**, 4. **Transmission**, 5. **rTorrent / ruTorrent** — implemented 2026-10-03 (`deluge.py`, `transmission.py`, `rtorrent.py` in `nazgarr/adapters/torrent_client/`, `adapter_type` `deluge`, `transmission`, `rutorrent`). **No new dependency**: each API is simple enough for `httpx`, already in the stack, and the standard library (decision taken 2026-10-03, the library choice was open in section 15):
   - **Deluge**: the JSON-RPC API of its **Web UI** (`/json`, cookie from `auth.login`), which forwards every `core.*` daemon method. Chosen over the daemon RPC (`deluge-client`, port 58846, rencode over TLS, a separate auth file) because `base_url` is always an http(s) URL and the Web UI is what users expose. Password only (the Web UI has no user). If the Web UI is not connected to a daemon, the adapter connects it to the first one it lists. Category = label of the Label plugin, only when the user has turned that plugin on (Nazgarr never turns plugins on); labels are lowercase; no tags. `skip_check_verified` uses libtorrent's `seed_mode`. **Recheck outcome** (audit 2026-10-18): Deluge's `state` is a value it keeps in memory and updates on libtorrent's events, `paused` is libtorrent's flag read fresh, and `is_auto_managed` is Deluge's stored option (true also while the torrent is paused), never read. No outcome yet (`pending`): "Checking" or "Allocating", "Queued" (Deluge's own state for paused and auto-managed in libtorrent), a paused torrent shown in another state (right after `force_recheck` Deluge shows "Seeding" or "Queued" at 0% for a moment, seen on the real instance; reading it as a result would fail a good recheck), and a "Paused" one that libtorrent no longer pauses (`force_recheck` resumed it for the check, Deluge has not caught up yet). "Paused" below 100% with the flag is a failed recheck: Deluge's `force_recheck` pauses again, after the check, a torrent that was paused. Before, paused and `is_auto_managed` read as `pending`, so a reseed added paused whose recheck failed stayed `pending` for good (never marked failed), and one missing only its known extras never started. After `force_recheck` on a paused torrent (a reseed, or its retry) the adapter waits, at most 5 s, for the read to stop looking like a failed recheck, which covers the moment before Deluge sees the check start; a small torrent whose check already failed waits those 5 s and reads failed, as it should.
   - **Transmission**: its JSON RPC (`/transmission/rpc`, `X-Transmission-Session-Id` handshake), chosen over `transmission-rpc` to avoid a dependency for one POST. No categories: tags become `labels` (RPC 16+, Transmission 3.0), `list_categories()` is empty. Recheck with `torrent-verify`. **`rename-partial-files`** (user decision, 2026-10-19; seen on the real instance, audit 2026-10-18): with it on, Transmission's default, the check renames an incomplete file to `<name>.part`, even for a stopped torrent, so after a failed reseed recheck the hardlink in the seeding folder (for a torrent→client reseed, the user's own file there, maybe used by another torrent) kept that name. The adapter reads it with `session-get` (`partial_file_suffix()`, SDK 1.5; default `None` for every other client): the client's card in Settings shows a warning to turn it off (`GET /api/torrent-clients/{id}/warnings`, also in the connection test's `warnings`, code `rename_partial_files`), and after a failed reseed recheck, from the review queue or the upload flow, Nazgarr renames `<name>.part` back to `<name>` (`nazgarr/torrents/partial_files.py`), logged, only for files it placed or tracks: the renamed file must have a device and inode Nazgarr recorded (a library or seeding file matched to the candidate, whose hardlinks share it; for the upload flow, the files the target put in seed), be a regular file (never a symlink followed) inside the disk's seeding folders with no symlink in the folders above, and nothing may be at the original name. Where the client looks is asked to the client (save path and files of the torrent, translated with the path mapping), not recomputed. The torrent stays stopped, so the client does not rename it again until it is rechecked or started; a Retry finds the files under their names.
   - **rTorrent / ruTorrent**: rTorrent's XML-RPC, marshalled with the standard `xmlrpc.client` and sent with httpx, either to rTorrent's own endpoint (`/RPC2`) or through ruTorrent's `plugins/httprpc/action.php`; a bare ruTorrent address gets that path appended. ruTorrent 5.3's proxy (mode "sanitize") forwards calls it cannot rebuild as *untrusted*, and rTorrent 0.16.10+ refuses write commands there (`d.directory.set` on its own, `execute.*`): the save path and the label therefore travel as commands of the `load.raw`/`load.normal` itself, and removing with data through ruTorrent uses its `removewithdata` action (the erasedata plugin, set up the first time the ruTorrent UI is opened). On the direct endpoint the torrent's own files are removed with `execute.throw rm` inside the client. Category = ruTorrent label (`d.custom1`, URL-encoded); no tags.
   - **Transmission and rTorrent cannot add a torrent as already complete** (rTorrent would need fast-resume data written into the `.torrent`): their adapters set `can_skip_recheck = False` and always recheck, so executor and upload flow never record a skipped recheck for them (`seed_job.recheck_skipped`, upload event `added_to_client_verified`).
   - **Torrents always start** (2026-10-05): qBittorrent's "do not start the download automatically" and "torrent stop condition: files checked" left reseeds and uploads stopped after the recheck. qBittorrent now gets `stopped=false` and no stop condition on add, qui `paused=false`, and both start the torrent after adding it. The recheck itself never changes. **This now holds for new uploads only**: reseeds (since 2026-10-18) and the upload flow's reseeds and Retry seeding (since 2026-10-19) are added stopped (next point).
   - **Reseeds are added stopped and start only after their recheck passed** (user decision, 2026-10-18, superseding the 2026-10-05 decision above for reseeds; uploads unchanged). **The reseeds the upload flow offers are added stopped too** (user decision, 2026-10-19; §9, "Adding to the client"): the tracker's `.torrent` on library hardlinks, and Retry seeding. Left running, a reseed whose recheck failed downloaded the missing pieces into the files at the save path, which are hardlinks of the library files (the same bytes), with no approval. Stopping it when its seed job was reconciled (audit 2026-10-18) only narrowed that: the reconcile comes every 120 s between runs and not at all during a run, and a single differing piece (an MKV header edited in place) is rewritten within seconds. Every built-in adapter now adds a torrent stopped on request (`add_torrent(..., stopped=True)`, `can_add_stopped`): qBittorrent `stopped` (`paused` before WebUI API 2.11) with no stop condition, qui `paused=true`, Deluge `add_paused`, Transmission `paused`, rTorrent `load.raw`/`load.normal` without `d.start`. The forced recheck runs as always, never `skip_checking`: qBittorrent, qui and Deluge start a stopped torrent for the check and stop it again afterwards, Transmission and rTorrent check it stopped. The reconcile starts it (`start()`: qBittorrent `torrents_start`, qui bulk `resume`, Deluge `core.resume_torrent`, Transmission `torrent-start`, rTorrent `d.start`) only once the recheck passed: 100%, or only the extras known to be missing (`seed_job.expected_missing_bytes`, which the client then downloads). The reconcile runs every 120 s between runs, at the end of every run and when asked from an item's detail, so a reseed approved during a run starts when the run ends. A start the client refuses keeps the seed job in progress with the reason, tried again at the next reconcile (before, it became "seeding" with the torrent stopped for good); reaching seeding clears an earlier error. A failed recheck leaves the torrent stopped and the seed job failed, saying so. One that is running anyway (a plugin adapter without `can_add_stopped`, whose reseeds are still added running, or a torrent started by hand) is stopped when the seed job is reconciled, a protective action the user accepted (`stop()`: qBittorrent `torrents_stop`, qui bulk `pause`, Deluge `core.pause_torrent`, Transmission `torrent-stop`, rTorrent `d.stop`); when the client cannot be told, the seed job says to stop it by hand. A retry that finds the recheck good starts it. **Retry on a reseed left stopped with a failed recheck asks the client for a new recheck** (audit 2026-10-18, `executor.adopt_for_retry`): the client never rechecks a stopped torrent on its own, so reading it again answered "failed" even after the user fixed or restored the files. The user pressing Retry is the approval, and it is a check, never a start: the seed job goes back to in progress with its recheck pending, and the reconcile starts the torrent only if the recheck passes. A client that cannot recheck (a plugin without `recheck()`) only gets the status read again; a recheck the client refuses is a failed retry, the seed job unchanged. The failed seed job's message says the torrent was left stopped, and to recheck it in the client or Retry once the files are right. A client that cannot be told to start a torrent (a duck-typed plugin without `start()`, or one raising `NotImplementedError`) gets the seed job marked seeding with a note to start it in the client, instead of staying in progress for good with a warning at every reconcile. The skip-recheck exception (Nazgarr verified 100%, user decision 2026-09-29) adds the torrent running, as before. **The allowance for missing extras covers only their pieces** (user decision, 2026-10-21; audit 2026-10-18): the client reports how many bytes are left, not which pieces, so a differing video piece that fitted inside `expected_missing_bytes` counted as a good recheck, and the torrent started and rewrote it inside the hardlinks (the window between the full check and the add, or the full check turned off). Now a review-queue reseed whose recheck failed within that allowance starts only once Nazgarr has verified with its own piece hashing every piece that does not touch a missing extra, read where the client reads it (the hardlinks, or the file on the torrent side, also under the `.part` name Transmission gives an incomplete file). The missing extras are not read: a client that preallocated them with zeros must not make them look different. The pieces that straddle a missing extra and another file cannot be verified by anyone until the client has the extra: they are what the two pieces per extra of the allowance cover, and the only bytes of a present file the client may still rewrite. It stays bounded: a full check that already passed on exactly these files (the one before executing, a retry's, or one asked by hand, for the same info hash as the torrent in the client, with the same device, inode, size and modification time for every file it read; remembered in memory, the latest 200) is not read again. Otherwise the check runs in the background, in the queue of the full checks (one at a time, listed with purpose `extras`), on the `.torrent` the executor added to the client (kept in memory for the latest 50 such reseeds; after a restart it is downloaded again from the tracker), which must be the one in the client; the seed job stays in progress, saying so, until a reconcile reads the outcome. A torrent running meanwhile (a plugin adapter without `can_add_stopped`, or one started by hand) is stopped while Nazgarr checks, the same protective stop as after a failed recheck (or the seed job says to stop it by hand), and a 100% the client reports before that check passed does not count without it (audit 2026-10-18). Passed, the torrent starts; a later reconcile compares the files with what that check read (the same identity, or absent as then for a file whose pieces all touch a missing extra) instead of reading them again. A piece that differs or cannot be read fails the recheck, with the files it belongs to, and the torrent stays stopped; so does a check cancelled from the list of the full checks: Retry checks again on the files as they are then. A check that could not run (the tracker unreachable, the disk not answering) is tried again at the next reconcile; after three checks of the same seed job without an outcome that holds (errors, or files that changed after a passed check) the recheck fails, and Retry starts over. After a restart an unfinished check starts again at the next reconcile. **The upload flow's reseeds follow the same rule** (2026-10-21, audit 2026-10-18: the same rule for every reseed; before, they kept the plain byte allowance): the tracker's `.torrent` on the source's files, and Retry seeding of such a reseed. Their full hash check before the decision has already read exactly these files (the dupe's verification, `nazgarr/upload/verify.py`), so it now records the identity of every file it read (device, inode, size and modification time, stored with the verification, so it survives a restart), and a recheck within the allowance starts the torrent without reading anything when every file of the torrent outside the missing extras is still that file where the client reads it (a hardlink has the identity of its file). Otherwise (a file replaced or edited in place after the check, or a verification from before this rule, which recorded nothing) Nazgarr reads every piece outside the missing extras in the seed folder, also under the `.part` name, in the background in the queue of the full checks (not in their list: such a check belongs to no candidate), on the `.torrent` saved with the job, which must be the one in the client, and the target keeps waiting for its recheck (`seed_recheck_pending`) until a reconcile reads the outcome (`nazgarr/upload/extras_check.py`, in memory per target: after a restart an unfinished check starts again). The rest as for the review queue: the missing extras, recorded with the add (`missing`, next to `allowed`), are not read (for an add from before this rule, which recorded none, they are the files absent from the seed folder, never a video: an absent video stays among the files to read and fails the check, audit 2026-10-18); a torrent running meanwhile is stopped (`seed_stopped_while_checking`); a 100% the client reports before that check passed does not count without it; a piece that differs or cannot be read fails the recheck with the files it belongs to (`seed_pieces_failed`) and the torrent stays stopped, and Retry seeding checks again on the files as they are then; a check that could not run is tried again at the next reconcile, and after three without an outcome that holds the recheck fails. The event `seed_pieces_checking` says when Nazgarr reads; `upload.seed_checked` is unchanged (`recheck_failed`).
   - **Category and tags per reseed** (user decision, 2026-10-05): like an upload, a queued reseed can get its own category and tags in the client (`match_review.client_category` / `client_tags`, NULL = the client defaults with the anime check, "" = none), chosen in the review's details and used when it runs.
   - **Verified against real clients in Docker** (`scripts/test_real_clients.sh`, `tests/integration/test_real_clients.py`, skipped unless `NAZGARR_IT_CLIENTS=1`, never in CI): Transmission 4.1.3 (`lscr.io/linuxserver/transmission` 4.1.3-r0-ls363), Deluge 2.2.0 (`lscr.io/linuxserver/deluge` 2.2.0-ls383), rTorrent 0.16.22 with ruTorrent 5.3.14 (`crazymax/rtorrent-rutorrent` 5.3.14-0.16.22), rTorrent tested on both endpoints. The client's folder is mounted at a path the test process does not have (translated with `nazgarr/torrents/client_paths.py`) and the `.torrent` files live where the client cannot see them, so a path sent instead of the content would fail. Checked for single-file and multi-file torrents: info hash, recheck to completion, recheck reporting wrong data as incomplete, files and sizes, save path, category/labels, tracker, duplicate detection, a `.torrent` URL fetched by the client itself, `skip_check_verified`, removal without and with files. Run again on 2026-10-18 (audit, same images, the containers with no DHT, peer exchange, port forwarding or DNS): a reseed added stopped is rechecked and starts only with `start()`, one with wrong data stays stopped after its failed recheck, and the retry's `recheck()` of that stopped torrent, once the files are right, passes and leaves it stopped. That run found two bugs, now fixed: Deluge's failed recheck read as `pending` for good (the Deluge point above), and **through ruTorrent a recheck goes through its own `recheck` action** (`mode=recheck`, as its UI does): a forwarded `d.check_hash` answers 0 and checks nothing on a stopped torrent, so every reseed through ruTorrent stayed at 0% and failed (before 2026-10-18 the first check came from `d.start` anyway). It also showed that Transmission renames an incomplete file to `<name>.part` during the check (its `rename-partial-files` preference, on by default), stopped or not: handled since 2026-10-19 (the Transmission point above).

**Every adapter sends a local `.torrent` by content** (`base.local_torrent_bytes`): the client usually runs in another container and never sees Nazgarr's data folder; only http/https/magnet URLs go as URLs (same rule as the qBittorrent fix of 2026-10-03, where the path went in `urls` and failed with "No such file or directory"). **A reseed never hands the tracker's link to the client** (audit 2026-10-18): the executor downloads the `.torrent` itself through the tracker adapter (rate limit, host rule, size cap), checks that its info hash is the candidate's (read by the matching or by the full check) and adds those bytes as a temporary local file, with that info hash expected. With the link the client fetched its own copy, and nothing tied it to the one Nazgarr had matched and verified: a hostile tracker could serve the right torrent to Nazgarr and another one to the client, which then downloaded into the hardlinked library files. A different info hash fails the execution before any hardlink, and a download that fails is a failed execution to retry. A tracker plugin needs `download_torrent` for reseeds. **The added torrent is found by its info hash** (audit 2026-10-18): the caller's `expected_info_hash`, or for a local `.torrent` the hash of the bytes sent (`base.expected_hash`, the raw `info` span); only a URL falls back to "the first new torrent" since the snapshot before the add. qBittorrent and qui used that fallback for local files too, so a torrent another tool (Sonarr, autobrr, cross-seed) added in the same seconds was taken for Nazgarr's: its recheck, its start and the upload's save-path check went to the wrong torrent. Every built-in adapter now shares `require_recheck`, `local_torrent_bytes` and `wait_for_hash` (lowercase hashes everywhere). **`remove_torrent(info_hash, delete_files)`** (2026-10-03) is part of the contract for every built-in client (qBittorrent `torrents_delete`, qui bulk action `delete` with `deleteFiles`, Deluge `core.remove_torrent`, Transmission `torrent-remove`, rTorrent `d.erase`); only for an explicit user request.

All behind the same `TorrentClientAdapter` contract — `add_torrent`/`get_torrent_status` inherited unchanged from ratio-guardian §14, **`list_torrents()` replaces the original `list_tracked_paths()` sketch** (implemented in `nazgarr/adapters/torrent_client/base.py`, different from this early draft):

```python
class TorrentClientAdapter(ABC):
    def add_torrent(self, torrent_file_or_url, save_path, force_recheck=True) -> str: ...
    def get_torrent_status(self, info_hash) -> TorrentStatus: ...
    def list_torrents(self) -> list[ClientTorrentInfo]:
        """Every torrent known to the client, with its files (path_in_torrent + size).
        Needed to populate client_torrent/client_torrent_file (section 4), not just to
        know whether a path is tracked yes/no — orphan_torrent/ignored/seeding are
        derived from that afterwards, never computed by the adapter itself."""
```

**Indexing cost** (audit 2026-10-18): rTorrent's files and trackers come from one `system.multicall` per 100 torrents instead of two requests per torrent (falling back to one per torrent where the endpoint refuses the batch; a fault on one torrent still fails the indexing, never a partial list), and qBittorrent's file lists, one request per torrent since its API has no bulk endpoint, are fetched 4 at a time (qui 8). qBittorrent asks them only for the torrents that are new or changed since the last indexing (audit 2026-10-18, revision): a torrent with the same name and save path, complete then and now, whose stored files add up to its total size and match its content path when qBittorrent reports one, keeps the file list stored at the last indexing (rewritten with the current run, so the prune keeps it). A file renamed deep inside a folder changes none of that, so every indexing still asks the files of a different eighth of the torrents (`indexer.FILES_REFRESH_RUNS`): each list is read again at least every 8 indexings, and a client of 10,000 torrents costs about 1,250 requests per run instead of 10,000. A plugin can take part with `list_torrents(..., known=...)` (SDK 1.7). The client **Test** counts torrents with `count_torrents()` (one request, no file lists; default for a plugin: `len(list_torrents())`). **Check paths** asked to the client live (`?live=true`, or a client never indexed) uses `list_largest_files(limit)`: only the first 500 torrents (`api/torrent_clients.py` `LIVE_SAMPLES`; the check on the last indexing still reads up to 5000 from the database), each with only its largest file, without trackers or statistics (rTorrent one `system.multicall` of `f.multicall` per 100 torrents, qui one request per torrent instead of two, Deluge and Transmission one call with fewer fields; qBittorrent still one request per torrent, 4 at a time, since its API has no bulk endpoint, so its live check costs at most 500 requests instead of 5000); before, it fetched the whole listing with every file and tracker and used the first 5000, slow enough to hit a reverse-proxy timeout (audit 2026-10-18). Default for a plugin: `list_torrents()` cut down.

A disk/torrents_rel_path can be associated with several configured clients at once (a common case: qBittorrent for one group of trackers, rutorrent for another, on the same disk) — indexing (`nazgarr/torrents/indexer.py`) therefore aggregates across every client enabled for that disk, never assuming a 1:1 relationship.

### Path mappings between a disk and a client (user report, 2026-10-03)

A client can see a disk elsewhere: in another container, or mounted only on a subfolder. Example: Nazgarr `/data/torrents` is qBittorrent `/downloads`. The disk–client link (`disk_torrent_client`) stores a pair, like the Remote Path Mappings of Sonarr/Radarr:

- `local_rel_path`: a folder of the disk (empty = the whole disk);
- `torrent_client_root_path`: how the client sees that folder.

`nazgarr/torrents/client_paths.py` translates both ways:

- **Client → Nazgarr**, when indexing. The client's path is compared lexically, never resolved: it does not exist in our filesystem.
- **Nazgarr → client**, for the save path of a torrent being added. A path outside the mapped folder raises `client_cannot_see_path`. The client never gets a torrent with a path it cannot see.

The old root-only override is the case with an empty folder. It is configured from the disks dialog of a client (UI) or with `nazgarr client link CLIENT DISK --folder … --client-root …`.

**Checking the paths** (user decision, 2026-10-05, after a setup retrospective: a wrong mapping gave no signal, and the client's torrents silently showed as orphans). "Check paths" on a client card (`POST /api/torrent-clients/{id}/path-check`, `nazgarr/torrents/path_check.py`, `nazgarr client check`) takes the largest file of every torrent, from the last indexing or from the client itself if it was never indexed, translates it with the current mapping and stats the disk: the file must be there, with its size, inside a seeding folder. Read only. It reports how many are fine, which have no disk, which point to a disk path without the file, and which sit outside the seeding folders, with examples. For the files not found it suggests a mapping: it strips leading folders of the client path until the rest exists, with the same size, in a seeding folder (or the root) of a disk; the stripped part is how the client sees that folder, and the most voted pair per disk is offered, applied with one click. The clients tour goes through it after the connection test.

Silent failures that became signals (same decision):

- every scan adds a problem for a client whose files were not found on the disks at all, or with more than 10% of its files pointing to a disk path where they are not (download in progress below that);
- `torrent_client_root_path` must be an absolute Unix path; it is trimmed and loses its trailing slash (`client_root_not_absolute`);
- a path outside the mapped folder, or outside the disk, always raises `client_cannot_see_path`, also with an empty folder: the client never gets an invented save path;
- the folder for new reseed hardlinks and the upload folder must exist, on the disk's filesystem, inside a seeding folder (`folder_not_in_seeding`), checked when saved instead of at execution;
- a reseed that fails on a coded error stores its English text with the parameters, not the bare code.

## 6. Content identification (TMDB) and the matching engine

### Media resolver (inherits ratio-guardian §6)

Default: filename parsing (guessit) → TMDB lookup. Optional Sonarr/Radarr adapter for more reliable mapping, never assumed present.

**Searches TMDB finds nothing for** (audit 2026-10-18): a successful search is kept in `tmdb_search_cache` forever; a miss never is, since a title TMDB doesn't know today can appear tomorrow. A miss is remembered in memory for 24 hours instead, keyed on what was searched (content type, normalized title, year): before, every episode of a series TMDB doesn't return repeated the same search, at every run. A renamed file searches another title and is looked up at once; a restart forgets every miss, and so does a scan started by hand (`POST /api/runs`, audit 2026-10-18): whoever starts one has usually just fixed a name or knows TMDB added the title, so it is searched again at once. Scheduled runs keep the misses until their 24 hours are up. Only files still on their disk are resolved (a file that left has nothing to identify).

**Sonarr/Radarr adapter (implemented 2026-09-23, `nazgarr/integrations/arr.py`)**: read-only index built once per run from every enabled instance.
- **Identity:** it gives the identity of every file Radarr/Sonarr know (`tmdbId`, season/episode), used by `ArrResolver` before guessit + TMDB, which stays the fallback. It also works with no TMDB key for the files the *arr instances know.
- **Torrent of origin:** from the history, the torrent a file was imported from. The imported event links `importedPath`/`droppedPath` to a `downloadId`, and the grabbed event gives `guid` (for UNIT3D via Prowlarr, the download URL `…/torrent/download/<id>.<passkey>`) plus the info hash. The matching engine turns this into a single `source='history'` candidate: one `.torrent` download instead of a catalog search, with the same explicit confidence rules (size, then piece hash). It falls back to the catalog search when that candidate isn't plausible.
- **History read once, then only what is new** (audit 2026-10-18): every index (the run, the Not imported refresh, the upload flow's index when its 10 minutes are up) used to download the whole grabbed and imported history again, tens of seconds for a large, old instance, synchronously in the refresh request. The process now keeps what the index uses from each instance's history (the grab of every download, and for every import its download, the two paths' keys, the size and the movie or episode) and asks only for the events newer than the newest one it read, page by page until one it already has: usually one page. History events never change, so one deleted there stays here, which is still what happened. A history that does not continue the one read (the newest event is older than the last one read: emptied, or another instance at the same address) is read again in full, and so is the history of an instance whose address changed or that was disabled or removed. A restart reads it all once. The rest of the index (the movies, series, episodes and files) is read again every time, since it changes.
- **Path matching:** automatic, with no path-mapping config. The folder and file name plus the exact size must match, because *arr paths live in their own container namespace.
- **Posters:** Sonarr only exposes TVDB artwork, so a series' TMDB poster costs one `/tv/{id}` call per series, never a per-episode title search.
- **Season packs:** the imported events also map every file of a download (`droppedPath`) to the library file it became (`importedPath`), even after Sonarr renamed it. This is the most precise way to match a pack's episodes (see "Multi-file torrents" below). On the user's instance: 396 pack folders, 8838 files.
- **Bounded answers** (audit 2026-10-18): every answer from Radarr/Sonarr (the index, the connection test) is streamed and read with a cap (`nazgarr/core/http_limits.py`: 256 MB and 300 s for the index, 1 MB for `/system/status`); an answer over it skips the instance like an unreachable one. The instance's address goes through net_guard when an index starts, not only when it is saved. Sonarr's series are indexed as their episodes arrive, so only the few series fetched ahead stay in memory. A grab's host is compared with the tracker's base URL without the scheme's default port (`:443`, `:80`), which a `guid` may spell out; another port still counts.

**Extension for the grid view**: at TMDB resolution time, download and cache the poster (`tmdb_poster_path` → local image, section 4). A `media_item` with no poster available (very niche content, or TMDB doesn't have it) shows a placeholder in the UI, never a blocking error. Posters are cached at TMDB's `w342` width (audit 2026-10-18): no view shows one wider than about 200 CSS px, so it is enough at 2x, at about half the bytes of the `w500` used before (files already cached stay). The download is read with a cap (10 MB, `nazgarr/core/http_limits.py`) and written under a temporary name, renamed only when complete, so an interrupted download no longer leaves a truncated poster that was never fetched again. Tracker favicons go through the same capped reader.

### Multi-file torrents: season packs and releases with extras (implemented 2026-09-23, `nazgarr/torrents/layout.py`)

Every candidate is evaluated as a whole torrent, file by file. This replaces the Phase 4 scope reduction ("more than one file = confidence 0"), which also excluded every movie released with an `.nfo` or subtitles next to it.
- **The library scan records every file**, not only videos. Exclusions are a filter for views, counts and API lookups; an excluded file that is part of a torrent is still used to recreate it. Only videos get an identity and trigger matching.
- **Radarr/Sonarr webhooks** (user decision, 2026-10-06): instead of waiting for the next full scan, an import, upgrade, rename or file deletion updates only those files (`nazgarr/integrations/arr_webhooks.py`). Each Radarr/Sonarr instance gets its own webhook password (Settings › Integrations, shown once, regenerable); Radarr/Sonarr send it as the Basic auth password of the webhook connection to `POST /api/arr-hooks/{radarr|sonarr}/{id}`, outside Nazgarr's login. Events are queued in `arr_webhook_event` and applied by the scheduler every 15 s after 10 s of quiet, never during a run. The file is found under the media folders by trying the tail of Radarr's path (through `resolve_scoped`, never a symlink) with the same size: one stat and a partial hash, so only its disk wakes up. A new file joins the disk's latest scan, linked to the torrent it was hardlinked from (same inode) and identified with Radarr/Sonarr's data. The torrent it was downloaded with is registered right away too, from the client that has it (`downloadId`, the info hash for torrent clients: its files in the seeding folders and the torrent in the client, `seed_refresh.register_client_torrent`), so the file counts as seeding before the next scan and is never proposed for reseeding (reported 2026-10-09); a deleted or renamed one leaves the current state the scanner's way (back to an older scan number, never deleted), and only when it is really gone from its disk (audit 2026-10-18): among the library rows with the same folder, name and size, the one whose file is missing, or replaced by another file under the same name (another inode or size: an upgrade that keeps the name), with the path closest to Radarr's. A replaced row goes through the same forget, so the old torrent's seeding file is unlinked and the new file is linked to its own torrent by inode. A copy still there, on another disk or in another media folder, is never touched, and the same file still in place (same inode and size) is left to the next scan. Searching the trackers right after an import is optional (`arr_webhook_search`, off). The full scan stays as the safety net; more frequent client re-indexing and optional inotify are possible next steps.
- **Default exclusion presets** (user decision, 2026-10-05): from the Plex ("Local Media Assets", "Local Files for Trailers and Extras") and Jellyfin naming docs. *Media server artwork and metadata* (on by default) excludes every image by extension (jpg, jpeg, png, tbn, webp), since Plex also takes artwork named like the video, numbered or as episode thumbnails, plus nfo, `theme.*`, `theme-music/` and `backdrops/`. *Extras* (off by default) covers the extras folders and suffixes of both (Featurettes, Behind The Scenes, `-trailer`, `-deleted`...). *macOS and Windows system files* (`._*`, `.DS_Store`, hidden volume folders, Thumbs.db) and *.torrent files* are on by default, also for who had already saved their presets (migration 9).
- **Matching a pack's videos to local files**, most precise first:
  1. Sonarr history (`droppedPath` → `importedPath`);
  2. on the torrent side, the original names under the same root as the orphan;
  3. guessit season/episode on the pack's file names plus exact size (translated between episode orderings when needed);
  4. **by content** (user decision, 2026-10-13, issue #25), for the videos still without a file: the history only knows the names of the torrent Sonarr downloaded, and some trackers rename packs in ways guessit cannot read (`Show - S01 - 01 - Title.mkv`). Candidates are the episodes of the same series on the same disk with the exact size, not already matched to another video, hardlinks of one file counted once (`LocalFiles.media_by_series_size`, built once per run). The size only selects them: a candidate is accepted only when the sampled piece hashes of the `.torrent` match it and at least one whole piece was checked. Exactly one candidate must pass; two different files that both pass, more than `MAX_CONTENT_CANDIDATES` (3) files of that size, or no checkable piece leave the video without a file (`season_pack_partial`). The `.torrent` is downloaded and pieces are read only when this can make the pack whole and the orphan is among the files; each file's pieces are read once per run, also when the candidate is re-evaluated from the real `.torrent` and when the same torrent comes from another tracker (`SharedLocalFiles.piece_checks`, keyed on the file and the piece hashes it is checked against, since the audit of 2026-10-18). A pack that content could make whole but only with other files (met while searching another season) is `anchor_not_in_torrent`, not `season_pack_partial`: it is neither persisted nor added to `evaluated_packs`, so one of its own episodes evaluates it later in the run (2026-10-16, issue #25 comment: the S01 pack seen while searching S08E09 was then skipped for every S01 episode).

  Every file must be on the orphan's disk (hardlinks). `candidate_file.match_method` records how each video was found (anchor, history, name, episode_order, content, path); the Reseeding page marks the ones found by content.
- **Extras** (nfo, subtitles, sample) match by name, or by extension plus exact size when renamed. Extras with no local file are left for the client to download after the recheck. The recheck counts as ok only if what is left fits `seed_job.expected_missing_bytes`: those extras plus two pieces each for shared boundary pieces, and, since 2026-10-21 (user decision), only once Nazgarr has verified every piece that does not touch a missing extra (section 5, "Reseeds are added stopped"; the upload flow's reseeds as well since 2026-10-21). Anything else below 100% still fails.
- **Confidence:** the lowest of its videos (size → per-file mediainfo Unique ID → per-file piece hash, using the offsets from the `.torrent`, downloaded once per candidate). A pack with any video missing locally is `season_pack_partial`, confidence 0, never executed. User decision: a pack is only recreated whole; seasons collected episode by episode keep using single-episode torrents.
- **One evaluation per pack per run:** the other orphan episodes of the same pack reuse it, and a torrent already queued or running for another file never gets a second review. The one exception (2026-10-22) is the file whose proposal already holds the pack (a review in the queue or approved, or an execution): it evaluates the pack again itself (with the `.torrent` and the pieces already read in the pass), so it confirms, updates or drops its own proposal whichever episode met the pack first. Before, it skipped the pack like any other episode, and since the orphans are searched in episode order (audit 2026-10-18) a pack proposed for an episode that was not the first orphan of its season (every proposal made under the old order, the rows' and so the filesystem's) was skipped by its own episode: that episode's single replaced it, every episode searched after it got its own single and the ones before it got nothing, until the next search of the season; with pack and singles the pack proposal was simply lost, and on the torrent side the seed file's pack proposal became a single. A pack proposed for another episode covers an episode (keeps its single out of the queue) only while it can still serve it. It no longer does when it is now impossible for the file (its info hash in a client, an upload of Nazgarr, rejected by the user), when the catalogue just searched no longer returns it (trumped or removed), or when the pass rated it implausible: the pass keeps the outcome of every pack it evaluated (per disk), so this holds for the episodes that skipped the pack too. A pack whose `.torrent` could not be read in the pass uncovers the episode only when the episode holding the proposal is still to be searched in that pass (the files a pass searches are decided at its start): that episode fails to read it the same way (a failed link is not retried in a pass) and drops its proposal. Otherwise, as in a targeted search of one episode ("Search now", the search after an import), the proposal stays and so does the cover: before, the episode got its single next to the pack that contains it. Before, the cover held until the episode of the proposal dropped it, so an episode searched before that episode got nothing and one searched after it got its single. Which proposals a search leaves for a season no longer depends on the order its orphans are searched in, except in a pass cut short by the tracker's rate limit and, as before, for a season with copies on two disks, whose pack is evaluated once on the disk of the first episode that meets it. Every file of the torrent and its local match is stored in `candidate_file`, which the executor recreates from and the Reseeding page shows.
- **Torrents that don't concern the file are not stored** (audit 2026-10-18). The catalogue search is by the series' `tmdb_id`, so it also returns the singles of every other episode; before, each one was mapped onto the episode searched and stored at confidence 0, for every episode, at every search. A one-video torrent whose name guessit reads as another episode (a double-episode file that includes it counts as this episode, and so does one the episode-order translation maps onto it; the episode orders are only asked of TMDB and Sonarr for this when the torrent's numbers are not all episodes the library has, otherwise only orders already read in the run count) and whose size differs from the file's is skipped like a pack of another season; at the same size the pieces decide, as always. On the torrent side, a torrent in which the orphan's path is not found is skipped too: before, such a pack was stored as partial and added to the run's evaluated packs, so the seed files that really belong to it skipped it for the whole run. A catalogue result with an unsafe file or folder name (empty, `.`/`..`, a backslash, a NUL, a folder with `/`) is ignored, with the same rules as the paths of a `.torrent`. A candidate whose `.torrent` the matching could not read (a single file kept as the catalogue describes it; it has no piece length) never places a hardlink by the catalogue's names: the executor downloads the `.torrent` first, takes the folder from it and refuses when its files are not the ones the catalogue listed. This holds after a passing full check too, which learns the info hash and corrects the folder but also finds files by name.
- **A new search updates what the last one stored** (audit 2026-10-18). Every search, every `rematch_interval_days`, used to add every result again as a new `candidate` with its `candidate_file` rows, so the tables (and the queries on them) grew forever. Now the evaluation of a torrent for the same content, tracker and direction updates the latest row no review and no execution uses, with its files rewritten; a row a review or a seed job uses is never changed or deleted (`seed_job.candidate_id` cascades). Within one run each row is updated once, so two files of the same content (two versions of a movie) keep their own evaluation. After a catalogue search, the file's earlier unused rows (in the formats searched) that the search did not rewrite go: torrents the tracker no longer returns, singles of other episodes stored before this change, a pack another episode evaluated in this run. A one-off migration removed the duplicates already stored the same way (the newest unused row of each torrent stays, rows in use always stay) and compacts the file when it removed at least half of the rows. When the new search proposes the same torrent, in the same format and with the same outcome (recommended or to review), as the review already in the queue for that file and tracker, and recreates it the same way (the same torrent files on the same local files, and the same info hash and folder when both evaluations know them), that review stays as it is: before, it was rejected by the system and recreated identical every week, with a `review.decided` and a `review.created` event each time and the client category and tags chosen by hand lost. A file whose search finds nothing plausible any more drops its review, as before; a different mapping of the same torrent replaces it, so the full check and the execution use the new evaluation. When every plausible candidate is excluded (rejected by the user, already busy for another file, already in a client), the review in the queue stays only while it can still run: it goes when its torrent is now in a client or is an upload of Nazgarr not yet indexed, when the user rejected that torrent (also as the pack of another episode), when the new search rates it implausible, or when the catalogue no longer returns it. A catalogue search that leaves no candidate at all, because every result was skipped before being evaluated (the singles of other episodes), also drops a queued review on a torrent the catalogue no longer returns; a review on a pack another episode evaluated in this run stays, and so does one when only the Radarr/Sonarr history was read. The reviews and executions that make a torrent busy are read once per tracker pass, not once per orphan. A torrent the upload flow is seeding or has just seeded (an upload, or a reseed chosen in the upload flow; by its id on the tracker or its info hash) is not proposed as a reseed until the next index: the upload adds it to the client without indexing it, so until then the source file looked orphaned and "Search now" proposed adding the upload again. The window covers the targets still uploading or being added to the client, and the ones finished without an error, or done with their torrent held stopped waiting for its recheck (`seed_recheck_pending`, the upload flow's reseeds and Retry seeding; since 2026-10-21), after the start of the last finished run; after that the torrent is among the client's, or, if the user removed it, it is proposed again like any other. Since audit 2026-10-18 the upload flow also registers what it adds right away, as the reseed executor and the Radarr/Sonarr webhook do (`nazgarr/library/seed_refresh.py::register_client_torrent`, after every add to the client: upload, reseed, retry seeding): the torrent joins the client's indexed torrents and its files in the seeding folders become seeding files, so the Library shows the source as seeding at once. A failed registration, a database too busy to write right after the add included, is only logged and never fails the upload, the reseed or the retry (the next index catches up), and the window above still covers an index that ran concurrently. A failed target is never excluded.
- **What a run reads once** (audit 2026-10-18): the indexes of the local files (`LocalFiles`) are built once per run for every tracker and both directions, not once per tracker and direction. A targeted search ("Search now", the search after an import) reads and checks only the files of that content in SQL, and builds those indexes only for their disks (every match stays on the anchor's disk, so the result is the same), once for all the trackers it searches. The orphans are searched by series, season and episode, so the episodes of a series meet the tracker's 10-minute search cache and the first episode evaluates a new season pack (a pack already proposed for another episode is evaluated again by that episode, whatever the order: "One evaluation per pack per run", 2026-10-22). That cache, shared by every operation on the same tracker and token, drops the expired searches at every write and keeps at most 2000, the least recently used leaving first, and the cache of a token no longer in use goes once nothing in it is valid (audit 2026-10-18: nothing ever left it, so every title searched stayed in memory for the life of the process). A tracker pass keeps the last 256 `.torrent` files it read (each holds every piece hash: a long first pass on a new tracker used to keep hundreds of MB until its end); a link that failed is not tried again in that pass. The active reviews, executions and info hashes in the clients are read once per tracker pass too, but Nazgarr's own uploads, and which of the candidates' info hashes are now in a client, are read again right before each review is created (revision of the audit 2026-10-18): the upload worker does not wait for runs, and an upload still being prepared when the pass started, published and seeded during it, was proposed as a reseed to redo (recommended, and executed with automatic execution on, to fail in the client).

### Matching engine (inherits ratio-guardian §7-8, integrated with smartmediareseed)

Pipeline unchanged in structure (personal history if available → catalog search by tmdb_id → size match → mediainfo Unique ID match → explicit, explainable confidence, never opaque ML). **MediaInfo runs in a child process** (audit 2026-10-18, `nazgarr/library/mediainfo.py`): libmediainfo is native code reading files from outside (the watched folder, the library), and a crash in it killed the single process (API, scheduler, upload worker), which at restart resumed the same upload job and crashed again; a hang stalled a run with no end. Every read now runs `pymediainfo` in a short-lived child with a time limit (300 s), returning only text (MediaInfo's XML or report, never pickled objects), read in chunks as it arrives and cut off past 64 MB with the child stopped (only the last lines of its errors are kept), so a crash, a hang or a flood of output is an ordinary failure the callers already turn into "no MediaInfo". It isolates crashes and hangs, it is not a sandbox (same user). It costs about 80 ms per read (measured), once per file and kind thanks to the cache. The Unique ID is kept only in that in-memory cache: `media_file.mediainfo_unique_id` is never written. See ratio-guardian SPEC.md §7-8 for every verified detail (UNIT3D API shape, season pack handling, the limits of personal history via scraping).

**Tracker answers are read with a cap** (audit 2026-10-18, `nazgarr/core/http_limits.py`): the UNIT3D adapter streams every answer instead of letting httpx load and decompress it whole, refuses a declared `Content-Length` over the cap before reading, counts the decompressed bytes as they arrive and stops past the cap (20 MB for a `.torrent`, 32 MB for a JSON answer) or after 120 s in total. The adapter decompresses the raw bytes itself, never httpx: httpx expands each network chunk (up to 64 KiB) in one call and chains stacked encodings, so a 2 KB `Content-Encoding: gzip, gzip` body reached GB in memory before the first count (audit 2026-10-18, review). One gzip or deflate layer is decompressed in steps of at most 1 MiB; more than one layer, or any other coding, is refused, and the requests announce only `Accept-Encoding: gzip, deflate`. A gzip bomb or a huge body from a hostile tracker (or a man in the middle on an `http://` tracker) is refused before it fills the memory of the single process; an answer that is not JSON is an `UploadError`, like any other tracker failure. Every request to the tracker runs `nazgarr/core/net_guard.py` again, not only when its URL is saved, so a tracker name that later resolves to a cloud metadata address is never called; a `download_link` must be on the tracker's host (or a subdomain) and keep its scheme, never `http://` on an `https://` tracker (the passkey would travel in clear). net_guard also refuses Alibaba's metadata address (100.100.100.200) and an IPv4 hidden in NAT64 (`64:ff9b::/96`) or 6to4 (`2002::/16`); the rest of 100.64.0.0/10 stays reachable for Tailscale. A host that cannot be encoded (an empty label as in `x..tracker.example`, or one over 63 characters) is a refused destination, not a raw `UnicodeError` that would stop the matching. The tests never use the real DNS (`tests/conftest.py`).

**A candidate's download link is stored without the key** (audit 2026-10-18, `nazgarr/reseed/download_links.py`). A UNIT3D link is `/torrent/download/<id>.<rsskey>`: the key is personal (it leads to the passkey) and is encrypted in `tracker.rss_key`, but every `candidate.download_link` kept it in clear, so a copy of the database gave it away without `APP_SECRET_KEY`. The candidate now stores the link with the placeholder `rsskey`; the executor and the full check put the current key back from the tracker's adapter when they download the `.torrent` (`rewrite_download_link`), or take the link from the torrent's detail when no key is known or the tracker refuses the one it has (a pending candidate keeps working after a key change). An adapter that cannot put the key back (a plugin without `rewrite_download_link`) keeps its link as it is. A one-off migration removed the key from the links already stored.

**The catalogue search reads every page** (audit 2026-10-18): UNIT3D's `/api/torrents/filter` is cursor-paginated (25 per page by default). The adapter asks for `perPage=100` and follows `meta.next_cursor` (or the `cursor`/`page` parameter of `links.next`, never the link itself), each page through the rate limit, up to 10 pages. Past that cap, or when the tracker repeats a cursor it already sent (the pages after it were never read), the results are a `CatalogResults` with `truncated=True` and a warning is logged, so the upload dupe check can say it saw only part of the catalogue instead of looking complete.

**Torznab endpoints** (issue #33, `nazgarr/adapters/tracker/torznab.py`): a tracker of type `torznab` is a Torznab URL plus its API key, whatever software exposes it (Prowlarr, Jackett, an indexer that speaks Torznab itself), and is used for search, matching, reseeding and cross-seeding only: Torznab has no standard API to publish a release, so it never gets an upload profile and uploads stay with the tracker-specific adapters. The adapter reads `t=caps` (available modes, the parameters each accepts, the page limit, the categories; cached for an hour) and searches with what the endpoint declares: `tmdbid`, then `imdbid`, then the title (`q`, with the year for a film and the season for a series) only when the ids are not supported or found nothing (`TrackerAdapter.search_media`, which the matching calls with the library's identity; for UNIT3D it is the usual search by tmdb_id). Results are paged with `offset`/`limit` through the endpoint's own rate limit, a 429 or a Torznab error 500/501 stops that tracker for the run like a UNIT3D 429, and a result that declares another tmdbid/imdbid, has no size or only a magnet is dropped. Name, size and file count only choose which results to look at: a Torznab result lists no files, so the matching downloads the `.torrent` of a result whose size can hold the local file (and, for a single-file search, is not much larger) and evaluates it with its real structure and piece hashes, exactly like a UNIT3D candidate; a result whose `.torrent` cannot be read is never executable. Matches go to the existing review queue. The `.torrent` link must be on the endpoint's host (Prowlarr and Jackett proxy downloads); a redirect from it is followed with net_guard at every hop, a redirect to a magnet is an error. The API key in the download links is replaced by a placeholder before a candidate is stored and put back only to download (`strip_download_link`/`restore_download_link`), and a guid that contains it is stored as a hash. One Nazgarr tracker per indexer (Prowlarr: `/<id>/api`) keeps each indexer's rate limit separate and lets its `announce_url` recognize its torrents in the clients; an aggregated endpoint works but mixes trackers.

**New confidence signal**, a recommendation already written up in smartmediareseed's analysis and adopted here as a requirement: **piece hash verification** (BEP3 bencode parsing of the downloaded `.torrent`, byte-exact comparison against the local content) as an additional signal, stronger than mediainfo Unique ID alone because it's deterministic and not subject to the known limitation (same video, different audio → sometimes the same Unique ID). To be used to:
- raise confidence when size+mediainfo already agree but aren't absolutely certain;
- **the only signal acceptable for auto-executing the torrent→client direction** (section 3), where a higher threshold than the media→torrent case is needed, because there the file already exists and a wrong match adds a non-matching torrent in a way that's less recoverable with just a recheck.

**Sampled pieces in matching:** a size-only video is "piece verified" only when at least one of its own pieces was read and matched (audit 2026-10-18): a file smaller than a piece in a multi-file torrent has only pieces shared with its neighbours, which the sample never reads, so it stays a size-only match instead of a false 0.99.

**Full hash check (diagnosis):** matching verifies only a sample of pieces. From a candidate or an execution the user can run a check of 100% of the pieces (`nazgarr/reseed/full_check.py`), boundary pieces included. It reads the files where the client sees them first, then from the library (for an execution, the hardlinks are looked for where the executor put them, by the client's content layout: one rule, `nazgarr/reseed/placement.py`, shared with the executor and with the registration of a new seed; the seed job does not store the layout, so the folder where the library file has its hardlink wins. Before, the check always rebuilt the torrent's folder, and with qBittorrent or qui set to "Subfolder" or "NoSubfolder" it reported the seed files as missing, audit 2026-10-18), and reports per file the pieces that match, differ or can't be read, plus whether the info hash changed. It's read-only and runs in the background, one check at a time. It tells a different release apart from a wrong path when a recheck keeps failing, and never replaces the client's recheck.

**Full check before executing** (`verify_before_execute`, on by default, user decision): approving a review first runs the full check. Hardlinks and the add to the client happen only if every piece matches and every file is present at the right size. The only exception is extras missing locally, which the client downloads after its recheck; a check that passed is remembered, so the piece check behind that allowance (section 5) does not read the same files again. While the check runs, the review stays in the queue as "verifying", with progress shown in the notification. If the check fails, nothing is touched and the review stays in the queue with the reason. Automatic execution, when turned on, applies the same check. The setting can be turned off (Configuration > Matching & approval) to execute straight away on the sampled pieces.

**Exceptions to the recheck.** Uploads (user decision, 2026-09-30): the torrent of a new upload is created by Nazgarr from the very files it will seed, so it is added without the client's recheck, after checking that every file is at the seed path with its size and, once added, that the client reports that save path; otherwise a normal recheck. Reseeds (user decision, 2026-09-29): the opt-in setting `skip_client_recheck_when_verified` is off by default and requires the full check before executing. With it on, a torrent is added with `skip_checking` only when Nazgarr's full check just verified 100% of its pieces, no extra is missing locally (otherwise the client has to download it) and the info hash matches. Since the audit of 2026-10-18 the info hash always takes part: a candidate without one takes the hash of the torrent the full check verified, a check whose `.torrent` has another hash than the candidate's fails, and the executor only adds bytes with that hash, so the torrent entering the client unchecked is exactly the one verified. The seed job records `recheck_skipped`. The known risk is the short window between the check and the add. **A forced recheck on the client remains mandatory in every case** when adding to the client (never `skip_checking`) — the piece hash is a stronger matching signal, not a substitute for the client's own verification.

## 7. Library view: tree + poster grid

Two display modes over the same underlying data (the unified per-file state, section 3), user-selectable, inspired respectively by Auditorr (tree) and the explicit request for a poster grid:

- **Tree view** (revised 2026-09-23, superseding the original "one tree + detail panel" sketch): **two separate, symmetric views** built on the same component — "Media files" (the tree under `disk.media_rel_path`, from `GET /api/media-files`) and "Torrent files" (the tree under `disk.torrents_rel_path`, from `GET /api/seed-files`). Same information, different dataset. Each one is summary cards per state (count + total size) on top, a toolbar (state tabs, filename/path search, min/max size in GB, show excluded, and — Media files only — a Duplicates filter backed by `GET /api/library/duplicates`), and a real table (indented name with folder chevrons, size aggregated recursively on folders, state badge, hardlink info on hover). Filtering is client-side over the full file list. **Windowing** (user decision, 2026-10-21; audit 2026-10-18): only the rows in the visible part of the page's scrolling area, plus about 1,000 px above and below, are in the DOM, and the space of the others is kept by empty rows of their height, so the scrollbar is the whole tree's, and the column widths come from the header (a fixed table layout, badges wrap inside the State column, the "⋯" column is wider on touch screens, where its button is larger), not from whichever rows are mounted. With a search every folder opens and the rows can be tens of thousands; before, blocks of 300 rows were added while scrolling and never removed, so after a deep scroll a click, a pack tick or a keystroke redrew thousands of rows. The window moves when the visible part gets within 400 px of its edge. Rows differ in height (a name wrapping on touch, the badges under the name on a phone): each mounted row is measured, a row never mounted counts as the average of the first rows measured, kept until the width changes (which restarts the measurements), and the row at the top of the view stays where it was when heights or data change (a row measured taller than estimated, a seed finished, a file excluded). So after a jump (the scrollbar dragged to the middle) the view moves only by what the rows just measured above it gained, never by an estimate that changed for every row above it: recomputed on every measurement, the average moved the view by tens of thousands of pixels on a large tree, and content and scrollbar chased each other while dragging; a new filter or search is another list and is not followed. Some rows stay mounted out of the window: the one with the keyboard focus and the one whose context menu, "⋯" menu or popover is open (the popup is anchored to it, and focus returns to it). Tab and Shift+Tab from a row's last (or first) control go to the next (or previous) row that has one, mounted or not, instead of jumping past the empty space; the Up and Down arrows move between rows the same way (on the "⋯" button too, where Enter and Space open the menu). The pack selection, SHIFT ranges included, works on the data, so rows out of the window are selected as well. No new dependency (`hooks/use-virtual-rows.ts`, `lib/virtualRows.ts`). The browser's find in page only sees the mounted rows; the search box covers the whole tree. Still deferred: per-file tracker + tracker filter, seed count, "Open in Radarr", a flat view, copy paths / CSV export, inline mini-posters.
- **Grid view**: a card per `media_item` with a TMDB poster (placeholder fallback), title, year, status badge. Meant for quick visual scanning ("what do I have, what's missing, what's broken") rather than technical detail — that stays one click away (the same detail panel as the tree view).
- **Filters shared between both views**: by state (every state from section 3), by disk, by MediaPath/content_type, text search by title.
- **Reverse lookup from the torrent side** (inspired by Auditorr): given a torrent in the client, show which library file(s) it corresponds to (via hardlink) — useful to understand "why is this seeding" without having to search manually.

Both views share the same backend/API — it's just `?view=tree|grid` over the same filtered resource, never two separate data pipelines.

### Tracker filter (user decisions, 2026-09-30)

A global selector in the top bar (dashboard, library and torrent views) shows the seeding status for every torrent ("All trackers", as always), only for the configured trackers (a public tracker doesn't count), or for one tracker. A torrent belongs to a tracker when the host of its announce URL matches the tracker's announce or base URL (`nazgarr/torrents/tracker_scope.py`). With a filter, a library file is seeding only if it's in a torrent of that tracker; torrents on disabled clients don't count at all; the torrent view shows only that tracker's torrents plus the orphans (in no torrent), which can become an upload for any tracker. The choice is a setting (`tracker_filter`), so it stays as the default. The dashboard's current numbers follow the filter; its history is kept per filter from the first scan after the filter existed (`tracker_health_snapshot`), while "All trackers" keeps the global history on `run_log`.

## 8. Reseeding engine and execution

Inherits ratio-guardian §9-11 in full:
- A configurable confidence threshold per direction (defaults 0.95 media→torrent, 0.98 torrent→client, see the note in section 6). A match above its threshold is **recommended** in the review queue, not executed. **Nothing that modifies files or the torrent client runs without the user's explicit approval** (user decision, 2026-09-23, after a run auto-executed 20 reviews unasked). Automatic execution of recommended matches is an opt-in setting (`auto_execute_above_threshold`, Configuration → Mapping), off by default.
- **The review queue comes in pages** (audit 2026-10-18). `GET /api/reviews/queue?offset=&limit=` returns a page of the queue with the total; the Reseeding page loads the next page as the end of the queue comes into view, and after a decision reloads only the pages it has. The order is the page's: the single episodes of the same season, tracker and direction together in episode order, every other review on its own, groups in the order of their first review; a page always ends at the end of a group, so a season row is never split between two pages. `GET /api/reviews` still returns the whole queue in that order (the CLI). Every list (queue, executions, failed executions) reads what its rows need once for the whole answer: where each file already seeds, the clients, the latest execution of each candidate, the info hashes in the clients; before, each review cost about fifteen queries, two of them over the whole library. The candidates shown in an item's detail (the best one per torrent, 30 at most) and in the audit under a review (the latest evaluation per torrent, 100 at most) are chosen and capped in SQL.
- **A review is decided once** (audit 2026-10-18). Approving or rejecting takes the review with a conditional update: only while it is still in the queue (pending or recommended) and its candidate has no execution. Otherwise the answer is a 409 `review_already_decided`, before any full check or execution: a review the system closed (file now excluded, gone, identity changed), one already rejected or executed never runs again, and two approvals at once (a double click, "Approve all" while a row is still running, the run's automatic execution and the user's) execute once. A failed execution is retried from the executions list, never by approving again. A retry first follows the torrent if the client has it (nothing is created), and asks the client to recheck it when it is stopped after a failed recheck or was only found after a failed add (revision of the audit 2026-10-18: a reseed is added stopped and its forced recheck is sent once the client shows it, so a torrent that showed up after the wait had never been checked, and reading it said "Recheck failed" until a second retry). A torrent this execution did not send to the client is never followed: the add failed because the client already had it (another program, or the user, had put it there), or the execution failed before sending it (its message ends with "nothing was sent to the client"). The retry answers `seed_job_torrent_not_ours` and touches nothing, where before it adopted that torrent and could stop, recheck or start it; once it is removed from the client, the retry starts from scratch. One interrupted by a restart may have sent it, and is followed as before. The one exception is Nazgarr's own torrent arriving late: when an earlier execution of the same review sent its add and never learned its info hash (the wait for it timed out, the client failed after receiving it, a restart), and the client already has the torrent at the very save path this execution sends, the add's "already in the client" is that torrent, and the execution follows it with a recheck instead of failing as someone else's (audit 2026-10-18, revised: the retry started while the first add was still on its way failed that way, and the torrent stayed stopped and never checked). When the torrent the execution followed is no longer in the client, the retry adds it again from scratch (audit 2026-10-18; before, an error 500 and only delete was left). When it is back in the client after the execution failed for that, it is followed only at a save path this review could have sent it to (the folder of the new hardlinks with any content layout, or the folder already holding the files): elsewhere another program re-added that hash, and the retry answers `seed_job_torrent_not_ours` (audit 2026-10-18, revised). A retry that cannot run answers with its code (`seed_job_not_failed`, `seed_job_already_retried`, `seed_job_no_client`), one that runs and fails again with `seed_job_retry_failed` and the English text of its error, without keys (audit 2026-10-18; before, free text, sometimes Italian, that the UI and the CLI could not translate); the adapters' own messages, such as the timeout waiting for an added torrent, are English too. When it has to start from scratch and the full check before executing is on, that check runs first, exactly as for an approval, and the execution comes only if it passes (audit 2026-10-18: the retry executed straight away, even when the files had changed since). An execution already retried (its candidate has a newer one) is not retried again. The automatic execution re-checks each review before its full check and skips one decided meanwhile.
- Hardlink with the exact name the tracker expects (media→torrent direction only — in the torrent→client direction the file is already in the right place, only the torrent gets added to the client).
- Forced recheck, never skipped. The torrent enters the client stopped and starts only once its recheck passed (user decision, 2026-10-18, section 5).
- Periodic reconciliation of recheck status (async on the client). An execution that can never reach an outcome becomes failed, with the reason, so it can be retried or deleted (audit 2026-10-18): one left in progress without an info hash by a restart (at startup: nothing runs then; the retry follows the torrent if the client got it), one whose torrent the client no longer has (after 10 minutes in a row, counted from when this Nazgarr process first saw it missing and never from before it was added or retried: a client just restarted may not have reloaded it yet; audit 2026-10-18, revised: the 10 minutes counted from the add, so a reseed in progress for longer, a queued recheck or a big pack, failed at the first read of a client still loading its torrents, as the upload flow already avoided; only when the client answered and its adapter can look up a single torrent: an adapter that cannot, such as a plugin's, never makes an unreachable client look like a missing torrent), one added to a client that is now disabled or deleted (before, the first enabled client was asked, did not have it, and the check failed every two minutes forever). A client that answers neither the status nor the lookup of one torrent (unreachable, or dropping packets until the timeouts) is asked once per round: its other executions wait for the next round, counted as errors, so a round that holds the lock of the runs (below) never costs two timeouts per pending execution (audit 2026-10-18, revised: before, webhook events, "Search now" and the scheduled runs waited minutes for every round while that client was down). An adapter that cannot look up one torrent (a plugin) keeps checking its other executions. Nothing changes in the client or on disk.
- Bulk import mode (one-off full scan) + scheduled run (cron configurable from the UI), both on the same engine.
- **One thing at a time** (audit 2026-10-18, `nazgarr/reseed/exclusive.py`): runs never overlap, and the side work that writes the same tables (applying Radarr/Sonarr webhook events with their optional search, "Search now", recomputing Not imported, checking the pending rechecks, now or every 2 minutes from the scheduler, and deleting an execution) never overlaps a run or another side work. Side work holds the lock a run starts with for its whole duration: when a run is in progress or other side work holds it, it doesn't start (the webhook queue waits for the scheduler's next round, the API answers 409); a scheduled run that comes due meanwhile waits for it to finish instead of starting halfway, and "Scan now" waits up to 10 s, then answers 409. The 409 says what is busy: `run_in_progress` when a run is in progress, `side_work_in_progress` ("other work is in progress: Radarr/Sonarr events or a search, try again shortly") when only side work holds the lock, since no scan is running then and the run indicator shows nothing, and `side_work_seed_jobs_in_progress` ("Nazgarr is checking the reseeds in progress in the torrent clients") when the side work holding it is that check. "Check now" and deleting an execution wait up to 5 s for other side work before answering 409 (never for a run): the scheduler takes the lock every 2 minutes while executions are pending, usually for a moment, and the 409 came much more often (audit 2026-10-18, revised). The scheduler and the webhooks never wait. Before, side work only checked that no run was in progress and a run could start in the middle of it (two matchers on one tracker: an `IntegrityError` on `match_attempt` and the rest of that tracker skipped); the periodic check of the pending rechecks did so until the revision of the audit, and could reconcile the same execution as "check now" or a run (starts and stops sent twice to the client). When it finds the lock taken it waits for its next round.
- **The scheduled run** (audit 2026-10-18): a slot missed while the process was suspended (host sleep, `docker pause`, a frozen VM) runs once when it wakes up (`misfire_grace_time=None`, with `coalesce`); APScheduler's default grace of 1 s dropped it until the next day. **A slot missed while Nazgarr was stopped or restarting runs once at startup** (user decision, 2026-10-18; the jobs live in memory, so no grace setting covers a restart): the internal setting `schedule_last_slot` (`settings_registry.MANAGED_KEYS`, never written through the generic settings API) records when the last slot fired, also when it found a run in progress and skipped, and when a cron is saved, so the slots of an earlier or removed cron never count. At startup, if a slot of the current cron falls after it and before now, one scheduled run starts 60 s later (`scheduler._plan_catch_up`), however many slots were missed. It checks again when it fires, with the cron of that moment, and starts nothing if a slot ran meanwhile or the cron changed; otherwise it is a scheduled run like the others, through the same run lock, skipped while a run is in progress. With no reference (the first start with a cron, or a database from before the setting, where the start of the last scheduled run is used when there is one) it records the start time and catches nothing up. A stored cron that does not parse never stops the start: it is logged as an error and the app starts without a scheduled scan until a new cron is saved (`PUT /api/schedule`, the only way to write it). `GET /api/schedule` says so instead of calling it active: `enabled` false and `error` with APScheduler's reason, shown in Settings next to the schedule and by `nazgarr schedule show`.

## 9. Upload: creating and publishing a new torrent

Inherits ratio-guardian §16 in full, including the reasoning on what to reuse from Upload-Assistant (the `torf` library to create the `.torrent`, extended `pymediainfo`, `ffmpeg-python` for screenshots, dupe-check via the same `TrackerAdapter.search_by_tmdb`) and what not to reuse (no code taken directly from Upload-Assistant, which is in development freeze — only a domain reference for the shape of UNIT3D requests and tracker profiles).

Points that stay unchanged:
- Separate data domain (`upload_job`, `tracker_upload_profile`), never touches the reseeding entities.
- Tracker profiles bundled as seed data versioned in the repo, copied into the DB when a tracker is created, freely editable afterwards and never re-read from the file.
- Mandatory human confirmation before submission, as non-negotiable as the forced recheck in reseeding.
- v1 already includes mediainfo + screenshots (not deferred).
- **Time and size limits** (audit 2026-10-18): every ffmpeg command for the screenshots has a time limit (120 s; all the screenshots of an upload together 15 minutes, keeping what was taken), so one ffmpeg stuck on a malformed file no longer stops the whole upload queue. A cancel during the screenshots stops them before the next capture (and before the next image-host upload), as a cancel while hashing does; before, only the database changed and every capture still ran. The description template runs in Jinja's sandbox (no code), and the sandbox also refuses, before computing it, what would make one value huge: `**` and `*` with a result past 64 Kbit or a repetition past a million items (`9**(9**8)` held the whole process for hours), a text method, filter or format that would pass a million characters (`ljust`, `center`, `replace`, `join`, `indent`, `wordwrap`, `batch`, `%` and `format` widths), and a rendered text past four million characters; an arithmetic error is `upload_description_template_invalid` like a syntax error. **Done** (audit 2026-10-18, revision): a value grown in small steps inside a loop is stopped too. `~` and `+` past a million characters or items are refused like `*` (a `~` doubled in a loop reached 128 MB in 0.05 s), and every render has a budget: what its operations build, added up (16 million characters or items, counting every result of `~`, `+`, `*`, `%`, a call, a macro, a filter or a `{% set %}` block, also one thrown away later: a list of many texts of a million characters each), how many times its loops turn (500,000, `{% for %}` and recursive `loop(...)` alike: two nested `range(100000)` ran for hours), and its time (5 s). A real description uses a small fraction of it. **Done** (audit 2026-10-18, second revision): a value that repeats a reference is measured by its text, not its length. `[a] * 300` inside `[b] * 300` inside `[c] * 300` is 300 items at each level, but its text writes `a` 27 million times, and `str()`, `tojson`, `==` or a sort walk all of it in one C call that holds the GIL to the end (97 characters of template, no loop: 5 s of a frozen process and 1 GB; one number changed: minutes and tens of GB, an OOM kill, and the `preparing` target requeued). Every container the template creates (a list, tuple or dict literal, `*`, `+`, a call such as `dict()` or a macro, a filter, `namespace()`) is measured when it is created: how long its text would be, counting each repeated reference every time it appears. Past a million characters it is refused, so every later operation on it is bounded; the measures are remembered for the render, so measuring a new container costs only its direct items. The arguments of a call together have the same limit (a macro sees them in `varargs`, `cycler()` in `.items`). A namespace is the one value a template changes after creating it: it is measured again at each `{% set ns.x = ... %}` and each time its text is written, which also counts in the budget. The same applies to the other single steps that made a huge result from small inputs: a format that writes one argument many times (`('{0}' * 300000).format(b)`, `'%(x)s' * n % {...}`), the total of the widths in one format, `|sum` of lists (quadratic copying), `|join` of a text letter by letter, `|replace` and `|urlize` with long arguments, `|pprint` with its indentation, `str.translate`, and `bytes` like text (`*`, `ljust`, `int.to_bytes`). The time budget is checked after every comparison and test too, since `==` and `in` walk their values in C. Over a limit the render fails with `upload_description_template_invalid` and the reason. The template is also compiled when the upload profile is saved (`PATCH /api/trackers/{id}/upload-profile`), at most 100,000 characters: a broken or huge one is a `400 upload_description_template_invalid` there, instead of failing the first upload to that tracker, and so is one nested too deeply for Jinja's parser or Python's compiler (a `RecursionError` there was a 500). Compiling is safe: the operators that grow a value are never folded at compile time.

Implemented in Fase 6. Two things found while implementing, not in the original design: `tracker.announce_url` was missing from the schema entirely (`base_url` is the API host, `torf` needs the distinct personal announce URL to create a valid `.torrent`) — added as a nullable column, same additive-migration pattern as every other schema gap found mid-implementation. And `type_id` resolution from a filename is reliable only for `category_id`/`resolution_id` (content type, `screen_size`) — the REMUX/ENCODE/WEBDL/BDMUX distinction is too convention-dependent for a generic guess, so it stays an explicit best-effort default, always editable on the `upload_job` before confirmation, exactly as this section already specified ("resolved, editable before submission").

### Upload flow v2 (user decisions, 2026-09-29 — supersedes the single-file/single-tracker pipeline above)

The Phase 6 pipeline handled one file towards one tracker, synchronously inside the HTTP request, with a hand-typed TMDB id. v2 redesigns the flow around what the user actually does:

- **What can be uploaded**: a single movie, a single episode, a season folder as a *season pack*, a whole-series folder as a *complete pack*. Selection happens in a drawer that reuses the folder view and lets the user pick either a file or a folder.
- **One job, many trackers**: `upload_job` is the source (file or folder), its confirmed identity (TMDB/IMDB/TVDB/MAL ids, season(s)), the user's overrides, and the mediainfo/screenshots, all produced **once**. `upload_target` is one row per selected tracker, with its own action (`upload` / `reseed` / `skip`), proposed and approved release name, flags (anonymous, personal release, internal, stream), dupe-check results, `.torrent`, remote id and outcome. This is what makes "reseed on one tracker, upload on the other" possible. `upload_event` is an append-only log of every step, used both for live monitoring and for the history drawer.
- **Tracker selection**: every tracker with an upload profile is preselected; the generated torrent goes to the client configured on that tracker (`tracker.torrent_client_id`, first enabled client when null), the same rule reseeding follows.
- **One `.torrent` per tracker** (user decision): each tracker gets its own file (its announce URL and `source` field, hence a different info hash). The piece hashes are computed once and reused for every tracker's file.
- **State machine persisted in the DB, driven by an in-process worker** (same single-worker thread pattern as `nazgarr/reseed/full_check.py`, but with state in the DB so a restart resumes the queue instead of losing it). The frontend polls, like runs and full checks. Never two steps of the same upload at once (audit 2026-10-18): a wake-up for an upload already waiting for the identification/analysis executor adds nothing (the waiting one reads the state it finds when it starts), one that arrives while a step of that upload runs is kept and the upload is looked at again when the step ends, and an approved upload is executed only by the one-at-a-time queue (an old wake-up that finds it queued or running does nothing, and the queue never takes for an orphan a running upload another step still holds). Before, a cancel and resume while the first wake-up was still waiting ran two analyses together, and an old wake-up could run an approved upload outside the queue, which then ran it a second time.
- **Two human gates, and only two**: (1) confirming the metadata match (and the season, for series); (2) approving, per tracker, the action and the release name. Gate (2) **is** the mandatory human confirmation of this section: once both gates are passed the worker runs to completion on its own, which is what makes a queue of several uploads possible (user decision, 2026-09-29).
- **Scheduled uploads** (user request, 2026-10-09; `upload_job.scheduled_at`): at gate (2) the upload can start at a chosen time instead of as soon as it is its turn. It stays queued until then, the other uploads go ahead, and a scheduler tick every 30 seconds wakes the queue when the time comes; a time already gone means now. While it waits it can start now or move to another time (web UI, `nazgarr upload schedule`, `--at` on `upload new`/`continue`). Since hours or days may pass after the decision, a scheduled upload runs each tracker's dupe check again before anything else: a torrent that showed up in the meantime (identical or in the same slot, and not there at the decision) stops the upload to that tracker (`upload_dupe_appeared`); a tracker whose catalogue was cut (`CatalogResults.truncated`) is said in a warning event (`dupe_recheck_truncated`, audit 2026-10-18), and the upload goes on. Reseeds don't need it.
- **Identification**: the resolver returns a list of candidates (not just the first hit) shown as posters with the title overlaid and a Movie/Series badge, with a detail panel on click. Forced ids go through TMDB's external-id lookup (`/find`, which covers IMDB and TVDB). For series the detected season is shown with the episodes found against the ones TMDB expects; an ambiguous season gets a picker. Posters of candidates not in the library are served through a backend proxy (the TMDB key stays server-side).
- **Analysis before the trackers**: size and file list compared with the torrents on every client; Radarr/Sonarr history consulted when configured — a file that the history says was grabbed from a tracker is flagged loudly (it's someone else's release: a reseed is probably what the user wants, not an upload). Another upload not finished yet with the same videos (the same bytes: the same inode, also from another path) is said at the decision too, with a link to it (`other_jobs`, event `other_upload_same_files`; audit 2026-10-18): a season of a split folder confirmed by hand as the whole folder, or an upload created by hand for a release the watched folder already has, reached the decision with nothing saying another upload would publish the same files. A warning, not a block, like the others; the pack a split comes from and the uploads born from this one never count.
- **Dupe check per tracker**: the tracker's results filtered on the dimensions that actually make two releases the same slot (resolution, HDR/DV, source, remux vs not, season/episode, byte-identical size), the same dimensions Upload-Assistant's `dupe_checking.py` uses — reimplemented, not copied. A strong match proposes a full piece-hash check (`nazgarr/reseed/full_check.py`); a passed check turns that tracker's suggested action into `reseed`, executed through the existing reseed path (forced recheck, as always). A tracker that says its catalogue was cut (`CatalogResults.truncated`) gets a `dupe_check_truncated` event and a warning on its card at gate (2): the check may be incomplete (audit 2026-10-18). The user's UNIT3D download key (rsskey) learned from the tracker's answers is kept on the tracker, encrypted (audit 2026-10-18). The dupes' download links are stored with a placeholder instead of that key (`upload_target.dupes_json`; migration step 12 strips it from the rows stored before), like the reseeding candidates: the full hash check and the reseed put the current key back only to download the `.torrent`, or use the link of the torrent's detail on the tracker when no key is known (`nazgarr/upload/verify.py::dupe_torrent`, `nazgarr/reseed/download_links.py`). The API never returns a dupe's download link. An analysis that was cancelled, or overtaken by a newer analysis of the same job, stops: the result of the tracker search in flight is dropped (with the job cancelled, that target goes back to its previous state), no other tracker is asked and no target is written (audit 2026-10-18).
- **Release names**: values read from the MediaInfo (resolution, video codec, HDR/DV, every audio track and its languages, subtitles) and from the release name (type, source, service, edition, repack, group), with the user's overrides on top. The release name used is the one of the torrent already seeding the same files (hardlink), else the original name Radarr/Sonarr recorded, else the source name. The variables are the same for every tracker (`nazgarr/upload/naming.py` VARIABLES: title and local title, year, season/episode, edition, repack, resolution, source, type, service, video codec, HDR, bit depth, main audio track split into codec/channels/Atmos, every audio track, audio and subtitle languages, subs label, group); each tracker's **naming rules** (`naming_rules_json`) only order and format them, edited in the tracker's upload profile with one input per release type, the variables as insertable chips and a live preview: a main template, an optional one for series (e.g. without the year) and optional ones per release type, plus a few options (local title in the tracker's language, all audio tracks or only the main one, how to write languages, SDR label, separator). Previewed and editable before gate (2). **Upscales are editions** (user decision, 2026-10-05): "AI Upscaled", "AI.Upscale" and "Upscaled" are read as an edition, next to the ones guessit knows, and go wherever a tracker's template puts `{edition}`. The template decides: the generic default and the bundled ITT templates (movies and series) have it.
- **Freeleech** (user decision, 2026-09-30): each profile lists the freeleech percentages the tracker lets uploaders set (UNIT3D `free`), with a preselected one; chosen per tracker when creating the upload and again at gate (2). None listed = no freeleech choice for that tracker.
- **Bundled profile by address** (user decision, 2026-10-03): a tracker created at the address of a bundled profile (same host, with or without `www.`) gets that upload profile right away; the preset picked in the dialog, or `upload_profile` in the API (`auto`, a bundled key, `none`), decides otherwise. Inside the profile, **Restore** replaces everything (ids, naming rules, description, defaults) with a bundled profile: the one it came from, or any other for a custom profile, after a confirmation. A profile key is only ever one of the bundled profiles' keys, never a path (audit 2026-10-18).
- **Video codec label by release type** (user decision, 2026-10-03): one table for MediaInfo and for the name alone. Remux and disc AVC/HEVC, untouched web and TV (WEB-DL, WEBMux, DLMux, HDTV) H.264/H.265, encodes (encode, WEBRip, BRRip, DVDRip) x264/x265. The encoder found in MediaInfo only tells whether a file is an encode, never the label. The label follows the type even when the type is corrected by hand; a profile can rewrite it (`video_codecs`, e.g. `H.265: H265`).
- **Naming rules are versioned** (user decision, 2026-09-30, the one exception to "bundled profiles are never re-read"): a bundled profile's `naming` block has a `version`. At startup a higher version in the code replaces the rules of a profile the user hasn't edited; an edited profile is only offered the update (a banner with "use the new rules"), unless the bundled version says `force: true`. Category/type/resolution ids are never touched.
- **Naming rules are checked when saved** (audit 2026-10-18): the rules of an upload profile, in the save and in the preview, must have the shape `nazgarr/upload/naming.py` reads (`nazgarr/upload/naming_rules.py`: text for the separators and labels, text-to-text maps for templates and labels, a known style and a whole `multi_from` for the languages, a known `title`), else `400 upload_invalid_naming_rules` with the key. Unknown keys pass. Before, rules of the wrong shape (from the CLI, a config import or a script; the editor can't produce them) were saved and made every upload to that tracker fail in analysis, and the preview answered 500. The file naming rules get the same check, in their save and preview (`PUT /api/uploads/file-naming`, `POST /api/uploads/file-naming/preview`). Rules already stored that no longer have that shape (saved before the check, or by hand in the database) are not used: the default file naming rules, or the profile's naming convention, with a warning in the log, instead of failing every upload. The CLI asks the server first (audit 2026-10-18): `tracker profile naming --set` sends the rules to the preview, shows the names they give and only then saves them, so a hand-written file of the wrong shape stops there with the key at fault (and a file that is not a JSON object is a usage error); `config import` previews the new rules of every existing profile while it builds its plan, so they stop the whole file before any change (a profile the file creates has no preview yet: the server checks its rules when they are saved). Only a rejected rule is a usage error (exit 2); a read-only key, which cannot send that POST, skips the check with a line on stderr, so `--dry-run` still shows the plan, and any other error keeps its own exit code.
- **Overrides without overwhelming the user**: only the four ids are always visible. A collapsed "Detected details" panel lists category, type, source, resolution, season/episode, year, edition/repack, group, service, each showing the detected value as its placeholder so the user only touches what's wrong. An empty field falls back to the detected value, so an X next to the optional fields leaves a wrongly detected value out of the name instead (user request, 2026-10-16: a wrong group could not be removed): override `cleared`, a list of `nazgarr/upload/naming.py` CLEARABLE_FIELDS (edition, repack, hybrid, service, HDR, video codec, audio, audio languages, group, year). Not type, resolution and source: they give the tracker ids or raise the missing-source warning. A cleared field is neither the detected value nor a default (no releaser name for the group, no SDR label for HDR); a value written in it wins and puts it back. An "Advanced" section keeps a handful more (naming toggles, screenshot count, custom description, don't seed, skip dupe check). Overrides given when the upload is created (`POST /api/uploads`) go through the same checks as the decision's (audit 2026-10-18); before, a name like "." or any screenshot count passed unchecked. The long tail of Upload-Assistant's ~115 CLI arguments is deliberately left out of v1.
- **History**: queue and history tabs; each row shows poster, title, kind and one badge per tracker outcome, with a drawer for the event timeline, names used, links, mediainfo, screenshots, description and, on failure, what went wrong. A row's title opens it from the keyboard too (a link to the upload page, a button for the drawer; audit 2026-10-18), the click on the row stays the mouse shortcut. The queue tab reads only the uploads not finished yet (`GET /api/uploads?scope=active`), polled every 2 s while the worker is busy; the history comes in pages of 50, newest first, with "Load more" (`GET /api/uploads/history`, with the total for the tab), and reloads only when an upload leaves the queue or after an action (audit 2026-10-18: before, every poll sent the whole upload history, with one query per upload and one per tracker). Without `scope`, `GET /api/uploads` still lists every upload, for the CLI and for other instances on older versions. A remote instance on an older version without the paged history (the released 0.9.x: the request ends on `/{upload_id}` with a 422, or a 404/405) gets its history from that full list, finished uploads only, in one page (audit 2026-10-18; before, the whole upload page of that instance became an error). A history that still fails to load (a server error) is said in its own tab, with Retry, and the queue stays. An upload page keeps refreshing, every 10 s, while one of its torrents waits stopped in the client for its recheck (`seed_recheck_pending`), so the warning goes once it starts and Retry seeding shows up after a failed recheck (audit 2026-10-18; before, the page stopped refreshing right there).
- **Where uploads seed** (user decision, 2026-09-30): hardlinks in a per-disk folder for uploads (`disk.upload_rel_path`, set like the folder for new reseeding hardlinks), falling back to the seeding folder (`torrents_rel_path`) when not set. A source already inside the seeding folder seeds in place. A reseed decided in the upload flow places the tracker's torrent the same way, with the tracker's own file names. Same filesystem or an explicit error, like reseeding; always a forced recheck.
- **Existing `upload_job` rows are dropped** when the new tables are created (user decision: no real upload data to keep).


**Releases from a watched folder** (user decisions, 2026-10-02). Each disk can have a watched folder (`disk.watch_rel_path`, `nazgarr/upload/watch.py`). It can never be the disk itself, nor be or contain the media, torrent, new-hardlink (reseed) or upload folder, nor a folder a client downloads or seeds in, nor one that already holds library files (audit 2026-10-18, `watch_folder_has_library_files`: watching `media/Movies` started an upload for every film, and watching the folder for new reseed hardlinks made each reseed a release whose approval removed the files the reseed seeds from). A dedicated subfolder inside the torrent or media folder (e.g. `torrents/watch`, an empty `media/incoming`) is fine, and the other folders can never be moved inside it afterwards.

- **Starting:** every new video file or folder put there starts an upload on its own, to every tracker that has an upload profile, as soon as nobody writes to it any more (user decision, 2026-10-02). That means: no partial files inside, no write for 15 seconds, and the same size as at the previous check. Checks run every 10 seconds, not through filesystem events: inotify isn't reliable on Unraid FUSE shares, NFS or SMB. A file moved in starts at the next check; a copy starts 15–25 seconds after it ends.
- **Once only:** `watch_entry` remembers each entry, so a release starts one upload even after its job is deleted. The entry is taken in the same commit that creates the job (audit 2026-10-18: two commits, and a failure in between started a second upload of the same release). The folder is only a way in, so what is already inside when it is chosen starts too.
- **Episode orderings** (user decisions, 2026-10-04): a series can number its episodes in several ways: TMDB default seasons, TMDB episode groups (digital, DVD, absolute…), TVDB's aired order (what Sonarr reads) and TVDB's other season types. Release files follow whichever one their publisher picked.
  - **Model.** `nazgarr/library/episode_orders.py` turns each ordering into the same shape: seasons of episodes, each pointing to one or more reference episodes (TMDB default numbering). The mapping is many-to-many, so an episode aired two at a time (two titles, half the count) points to two references, and the reverse. TMDB groups carry the reference numbers; Sonarr and TVDB are aligned one to one when the counts match, in pairs when one is double the other, else by air date. **Positions hold only when the air dates do not contradict them** (user decision, 2026-10-18, audit 2026-10-18): when more than half of the positional pairs that have a date on both sides (at least two) are more than 3 days apart, the positions are shifted and the alignment falls back to the air dates, the same way as when the counts differ, except that a date with no identical one on the other side takes the one a day before or after, when there is exactly one and it is not also a date of the ordering being aligned. Totals can match by coincidence: a pilot one source keeps in season 1 and the other among the specials, plus a finale split in two on one side only, left every episode after the pilot off by one, with TMDB's generic titles unable to fix it. The 3 days tolerate what TMDB and TVDB commonly differ by (a day for time zones or a premiere in another country, sometimes two or three) and still catch a weekly show shifted by one episode (7 days). A show released in one day on either side never falls back (the dates cannot tell positions apart: a streaming drop on one source and the broadcast weeks on the other would all land on one reference), nor does one where at most half of the dates differ on one side (the two halves of an episode count once), nor one where fewer than half of the positional pairs have both dates (audit 2026-10-18). Titles then win over positions and dates (2026-10-15, after a TVDB DVD order of two-segment episodes, "Title A / Title B", that had one air date for nine episodes): an episode whose every segment title belongs to exactly one reference episode (case, accents and punctuation ignored, small typos tolerated, generic titles like "Episode 5" skipped) points to those. An air date with far more episodes on one side than the other (more than double and not a multiple) gives no reference rather than a guess. A title must also be unique in the ordering being aligned, a near-identical title needs the same numbers (roman numerals and number words count: `Part I` is not `Part II`), and it never takes a reference an identical title already owns (audit 2026-10-18). TMDB group parts named specials or extras, or with season 0 in the name, are season 0, together; the others take their season from their names only when those numbers are all different, otherwise from their position among the non-special parts, from 1 (audit 2026-10-18: "Season 1 Part 1/2" became one season and the second part's episodes were lost). Episode numbers in a part's name are positions, never a season (audit 2026-10-18, revision): "Episodes 13-24", "Ep. 25" or a range in brackets do not count, so "Episodes 1-12"/"Episodes 13-24" are seasons 1 and 2 (before, 1 and 13), and "Season 2 (Episodes 13-24)" stays season 2. A number that is not an integer or a title that is not text is skipped at the source, and an ordering that fails to align is left without references (audit 2026-10-18). Alignments and translations are computed once for the same pair of orderings and cached with the orderings. A file with several episodes (S01E01E02) keeps all of them, translated, in its generated name.
  - **Sources.** TMDB default and groups (with the TMDB key); Sonarr's episode list when the series is there (from the first enabled instance that has it, highest priority first and no priority as 0, the same order as the run's index; before, the lowest priority won, audit 2026-10-18); TVDB's API (`tvdb_api_key`) only as the last resort, when Sonarr doesn't have the series or the files don't follow its order (another TVDB order, e.g. "Joined", may cover them). Ties go to the series' last choice, then TVDB aired, then the other TVDB orders, then TMDB.
  - **At the first gate of an upload** (`GET /api/uploads/{id}/episode-orders`): Nazgarr scores how well the files fit each ordering, season by season and by number, never by position. For a pack or a library the number of episodes in each season comes first (75%), then whether the files' numbers exist in the ordering (25%); for a single episode only the numbers count. Separately, the ordering in which the files' numbers exist (ties broken by the season shape) is the numbering the files are translated from: a library numbered by Sonarr can follow TVDB aired in its numbers (three segments per file, the first one recorded) while its files are the episodes of another ordering. The best fit is selected by default; ties go to the ordering last chosen for the series, then TVDB aired, then TMDB. Without episodes in the files, that same priority applies. The user can always change it. A warning appears only when the files do not follow TVDB aired, Sonarr's order, and only if TVDB aired is known (from Sonarr or the TVDB key), with a shortcut to switch to it. The season picker, the episode counts and a file-to-episode preview follow the selected ordering. Without TMDB's default seasons (no key, or an error) no ordering has references, so nothing translates: the files' ordering is proposed (audit 2026-10-18).
  - **After the match.** The chosen ordering is saved on the job (`episode_order`, plus the data to translate numbers) and as the series' preference. Its numbering is used everywhere after the match: release name, generated file names (files numbered after another ordering are renamed into it, a merged episode becomes `E03E04`) and the tracker's season and episode fields. An automatic match uses the best fit too, and logs a warning when it is not TVDB aired. Episodes of the files that the chosen ordering does not have keep the files' numbers: the `episode_order_untranslated` event lists them, the match card at the decision shows it, and in a pack such a video keeps its own name instead of a generated one (audit 2026-10-18). A single-file upload of a merged episode, or of a file holding S01E01E02, is named with all its episodes as in a pack, both its files and the title proposed for each tracker, when they start from the episode confirmed at the match; the tracker's episode field stays the first one (audit 2026-10-18).
  - **Reseeding.** When a pack's files can't be found in the library under their own numbers, the matching engine translates them. It works out the torrent's ordering (best fit of its episodes) and the library's (best fit of the library's episodes, usually Sonarr's), then maps each episode through the references (`map_media_side`, `Translator`). Only one-to-one translations onto an existing library episode count: a file holding two merged episodes never becomes a single library file. The orderings of a series are collected once per run and cached for an hour.
  - **Library.** The series sheet offers the same orderings, scored like a pack (13 files out of 13 beat 13 out of 38, e.g. TVDB "Joined" against aired segments) (`GET /api/library/items/tv/{tmdb_id}/episode-orders`). By default it shows the files' own numbering, with the episode titles; picking another ordering regroups seasons and renumbers episodes, and each season shows how many episodes that ordering expects. A note appears when the library doesn't follow TVDB aired.
  - **Not yet.** The upload dupe check doesn't translate the seasons of torrents already on a tracker: their ordering can't be told from the name alone.
- **Resuming a cancelled upload** (user decision, 2026-10-03): a cancelled upload resumes from where it stopped (`POST /api/uploads/{id}/resume`, Resume in the upload page and the history, `nazgarr upload resume`). At an approval gate it comes back to that gate with the choices already made. Identification or analysis start again. A cancelled execution goes back to the queue with only the trackers not yet done: a tracker already uploaded is never uploaded again, and with nothing left the resume is refused. A cancel that lands while the last tracker is being sent stops nothing: when that tracker then fails, the resume sends nothing and ends the upload partly done, as the execution would have (`job_partial`, `after_cancel`), and Retry takes the failed tracker from there with its usual checks (audit 2026-10-18; before, neither Resume nor Retry accepted it, and a release from the watched folder, kept there for Retry, stayed for good). The same holds when the tracker being sent may have received it (a timeout, a server error, an answer Nazgarr can't read, or a restart: `upload_outcome_unknown`, `interrupted`), also with a single tracker or with every tracker failed: the resume ends the upload failed or partly done with that warning kept, and Retry asks for its confirmation (audit 2026-10-18; before, the resume sent it back to the analysis, whose dupe check can't see a torrent still in moderation, the warning was cleared, and approving again uploaded it twice). The state at cancellation is stored in the `job_cancelled` event; older jobs infer it from their data. A source that no longer exists cannot be resumed.
- **Retrying a failed upload** (user request, 2026-10-18): an upload that ended failed or partly done can be retried (`POST /api/uploads/{id}/retry`, Retry in the upload page and in the history drawer, `nazgarr upload retry`), so a temporary or fixable problem (the tracker down, the image host, a folder's permissions) doesn't force going back through the match. It retries every tracker that failed before publishing, upload or reseed; one that published but did not seed keeps Retry seeding. The decision stays as it was (name, ids, flags, reseed, client category and tags); the upload goes back to the end of the queue and, before sending, the dupe check runs again as for a scheduled upload, with fresh results (not the search cached by the analysis): a torrent that appeared meanwhile stops that tracker. A tracker whose sending may have reached the tracker is retried only after an explicit confirmation, once the user has checked on the tracker (`confirm_interrupted`, `--confirm-interrupted`): one interrupted by a restart, and one that failed after the request went out (`upload_outcome_unknown`, audit 2026-10-18: a timeout on the answer, a server error, an answer Nazgarr can't read; the tracker may have stored it, and UNIT3D's search doesn't list torrents still in moderation, so the dupe check would not see it). Only a connection that never opened and a 4xx answer (the tracker refused it), when the adapter shows them as the cause of its error, count as not sent; a failure while preparing (the profile, the announce URL, the screenshots) never asks. Screenshots already on the image host are reused. A split upload, a busy one or one whose source is gone cannot be retried; the source must still hold what goes into the torrent (a single file, or a folder or pack with a video), not just its folder. A release from the watched folder stays there while any of its trackers failed (user decision, 2026-10-18, see "A way in, not a home"), so Retry still has its files; before, it left once one tracker succeeded and the retry was refused. A source that left anyway (an upload from before that change, or one moved by hand), with only a sample or an nfo, is refused (`upload_source_missing`).
- **Errors during execution** (audit 2026-10-18): any error while preparing the torrent (a hardlink refused by the filesystem, a disk read error while hashing, an image-host plugin) fails the uploads with that error, in the log and in the job's events (`upload_prepare_failed` when it has no code of its own); reseeds go on. Before, everything but Nazgarr's own errors ended the job as "step not available" with no trace. A cancel in the middle removes the hardlinks made for the torrent's names, as the end of a job does. Those hardlinks are also recorded in the job's folder (`links.json`: path, device and inode, audit 2026-10-18), so the cleanup of a later run of the same upload (a resume after a restart, a Retry) removes the ones an earlier run left, which it reuses without creating them, and deleting an upload removes the ones that seed nothing, with the same rules (never with an upload that succeeded and seeds, never one another tracker or a client torrent seeds from, only if it is still the same file). Another upload with the same names reuses such a leftover link without creating it: a link another upload seeds from (its trackers done or seeding, from their `seeded-<target>.json`) or builds its torrent from while it runs (`content.json` in its job folder) is kept too (audit 2026-10-18, review of finding 115). Before, they were known only in memory: a run stopped halfway or a failed cleanup left them in the seed folder for good. Cleaning up afterwards (unused hardlinks, the watched folder) never changes the outcome: a failure there is a warning event. A tracker that accepted the upload is never marked failed afterwards, whatever goes wrong next (the client, the database): it is published but not seeded (`seed_failed`, retry seeding). Its torrent id is also written to the job folder before the database, and committed again a few times if the database is busy, so a restart in that moment still knows the upload went through. A restart while a tracker's torrent was going into the client leaves the upload published and not seeding, with Retry seeding, instead of stuck in "seeding"; an interrupted reseed fails and can be retried. The same holds without a restart: when the execution stops on an error the worker could not even record (the database not writable), the queue takes the job up again 30 seconds later, sets its trackers right as at a restart and finishes the others; when it does record it, no tracker is left "being sent", the ones still to do fail with that error (so Retry takes them), and with a tracker already done the upload ends partly done. An upload cancelled while a tracker is still being sent is neither deleted nor resumed until that tracker is finished (`upload_job_busy`): deleting it then lost the record of a torrent already on the tracker.
- **What enters the torrent** (audit 2026-10-18): a torrent built from the hardlinks made for its names holds exactly the files the decision showed. The folder with that name in the folder for uploads may already hold other files (the original release with another tracker's promo, an earlier upload with a subtitle removed since): they stay where they are, out of the torrent, listed in a warning event. The file list of the torrent is checked against the plan before anything is hashed or sent: one that still differs (an extra torf could not leave out, a planned file missing) stops the upload (`upload_torrent_files_mismatch`, `upload_planned_files_missing`), and so does an empty plan. Empty files never enter (torf leaves them out). A source used as it is (original names) is checked again for symbolic links right before hashing, since days can pass after the job was created and torf follows them.
- **Adding to the client** (audit 2026-10-18): every add from the upload flow tells the client which info hash to wait for (computed from the exact bytes of the .torrent), as reseeding already did: qBittorrent and qui otherwise took any torrent that appeared meanwhile (another tool's add) for ours, and the skip-recheck path check looked at that one. A torrent the client already has (an earlier attempt that got there before failing, or one added by hand) is kept, with a recheck, only if it uses the very same folder; elsewhere the add fails with that folder and nothing is moved. **Retry seeding** seeds from the folder for uploads, never from a library folder: when the hardlinks there are gone (removed as orphans, or the folder created after the error) they are made again with the torrent's names; only a source already inside the seeding folder seeds in place, as in the normal flow. It adds the tracker's own .torrent: the copy saved after the upload, or downloaded again from the tracker when the seed stopped before that; Nazgarr's own .torrent (whose info hash a tracker that rewrites the source field does not know) only when the tracker can't give it back, with a warning. **The tracker's `.torrent` on Nazgarr's files enters the client stopped and starts only once its recheck passed** (user decision, 2026-10-19, as the reseeds of the review queue since 2026-10-18): the reseed the upload flow offers and Retry seeding, never a new upload, whose torrent Nazgarr has just created from those very files (its documented behaviour, user decision 2026-09-30, is unchanged). Left running, a failed recheck downloaded the missing pieces into the hardlinks, the same bytes as the library files. The add is the adapter's `stopped` (a plugin without `can_add_stopped` adds it running, and a failed recheck stops it); a torrent the client already has in the same folder is kept with a recheck and no start. The target is done (the reseed or the upload is made) with `seed_recheck_pending`, the result says the torrent waits for its recheck, and the event of the add keeps the save path and the bytes of the extras the source lacks (`expected_missing_bytes`: the client downloads them after the start). The scheduler reads the outcome every 30 s (`execute.reconcile_held_seeds`, never on a job the worker is running, also during a run; a job only waiting in the queue, e.g. after Retry of another tracker, is not running: audit 2026-10-18, before, its torrent stayed stopped until that retry had waited for and hashed everything ahead of it): passed (100%, or only those extras missing, once Nazgarr has verified every other piece: §5, since 2026-10-21), the torrent is started and the warning goes; a start the client refuses is tried again at the next round; a client that cannot be told to start it says so. Failed, it stays stopped (one running anyway is stopped), the files the client renamed to `.part` get their names back (§5, Transmission), and the target says `seed_recheck_failed` with the client's state. So does a torrent no longer in the client, or whose client was removed from Nazgarr. As for the review queue's reseeds (audit 2026-10-18), a torrent the client does not list counts as gone only after 10 minutes in a row (`MISSING_TORRENT_GRACE`), counted from the latest add or recheck request and from when this Nazgarr process first saw it missing, so a client and Nazgarr restarted together, with the client still loading its torrents, do not fail a recheck that would pass; and only when the adapter can really look up one torrent (a plugin with the base `get_torrent_info`, which asks the client nothing, never reads as gone: there Retry seeding only asks for a recheck). A torrent the client already has in the same folder, or one rechecked again by Retry seeding, is stopped first when it is running (added by hand, or by an attempt from before 2026-10-19): rechecked running, a failed check resumed the download into the hardlinks until the next round. While a target waits for its recheck, its job cannot be deleted (`upload_seed_recheck_pending`): the target and its add event are all the reconcile follows, and the torrent stayed stopped for good with nothing saying so; once the recheck has an outcome it can, and so it can when the target's client is disabled or removed, which the reconcile does not follow anyway. The outcome arrives after the job has finished: `upload.finished` says done, with the target waiting for its recheck (`seed_recheck_pending`), and **the outcome is the event `upload.seed_checked`** for webhooks and notification services (user decision, 2026-10-21), emitted once when the held recheck resolves, with the job, the target, the tracker, the client and `outcome`: `started`, `start_by_hand` (passed, but the client cannot be told to start it), `recheck_failed` (with the client's state, and whether it is left stopped) or `gone` (no longer in the client after the 10 minutes, or its client removed from Nazgarr). A start the client refuses emits nothing until a later round starts it; Retry seeding puts the target back in waiting, and its outcome is a new event. `upload.finished` is unchanged; the payload is in docs/SDK.md (SDK 1.6). From there **Retry seeding** works for a reseed too: with the torrent still in the client it asks for a new recheck, never a start, and the target waits again; without it the same `.torrent` is added again, stopped, in the same folder for a reseed (inside the seeding folders), or as before for an upload. The job keeps its outcome: a failed recheck is not a failed tracker, nothing gets published or linked again. On the upload's page and in the history drawer a published tracker's state reads as a translated warning in amber, a recheck still pending (a clock, not an error) as well as a failed one, and Retry seeding is offered for a reseed after a failed recheck, never while the recheck is pending (audit 2026-10-18; before, the drawer showed the raw code in red and the page offered the button only for uploads).
- **Specials** (user decision, 2026-10-03): season 0 can always be picked in the match step, listed last as "Specials". A `Specials` folder (the Plex, Jellyfin and Sonarr convention) is season 0 for the episodes inside it.
- **Built-in notification services** (user decision, 2026-10-03): Discord (a channel webhook, sent as an embed coloured by level, mentions disabled) and Telegram (a bot token and a chat id, with an optional topic id, HTML-escaped text). They use the plugin notification contract. The webhook URL and the bot token are secrets: they never appear in error messages.
- **Notification services are instances** (user decision, 2026-10-05): any number per type (a Telegram bot and a Telegram channel, two Discord channels...), each a row of `notification_service` with a name, its encrypted configuration, its events and a message format (`standard` only for now: the column is there so a service can later get a different text, such as a compact one, without a migration). Settings > Extensions > Notifications lists them together with the webhooks: an "Add" button picks the type (built-in, plugin or webhook), the configuration is edited in a dialog that can send a test before saving, and each instance is a card with the type's icon and a recap of its configuration (secrets only as "set"). Deleting an instance deletes its deliveries, including the queued ones.
- **Notices:** each release triggers a notice in the app wherever you are (`GET /api/uploads/notices`), once when it is detected and once when it is ready for your decision, with a button that opens the upload. The events `upload.detected` and `upload.ready` go to webhooks and notification services, and so do `upload.finished` and, for a torrent added stopped, `upload.seed_checked` (see "Adding to the client").
- **Releaser name:** the setting `upload_releaser_name` becomes the `{group}` override of these jobs, and stays editable. On any other upload it fills `{group}` when the release name has none (user decision, 2026-10-03).
- **Automatic match:** TMDB candidates now carry a confidence (`nazgarr/upload/match_score.py`). The file name is also compared with the titles in the job's tracker languages: one extra TMDB search per language, which also finds the candidates that only the translated title reveals. Every upload, by hand or from the watched folder, confirms its best candidate on its own when the confidence is at least `upload_auto_match_threshold` (default 0.9; 0 turns it off). Ambiguous candidates (two titles nearly as sure) are never confirmed on their own. A name without a year can only be checked to 0.85 on the year, except for a series (user decision, 2026-10-13): TV release names almost never carry the year, so a series whose title is exactly the name and is the only series among the candidates with that title is not lowered by the missing year (`year_waived`). Two series with the same title (The Office UK and US) still need the year. Candidates are scored, ambiguity included, on every result before the list is cut to the first eight (audit 2026-10-18: a same-titled series ninth or later didn't count).
- **Where it stops:** the job goes as far as the decision and waits there. Nothing is uploaded, linked or added to a client without approval.
- **A way in, not a home:** the watched folder is only a way in. A release from it always seeds from the upload folder, hardlinked there before publishing, also with the original names (user decision, 2026-10-05: names untouched, folder changed; before, original names seeded in place when the watched folder sat inside the torrent or upload folder, and the release stayed there). Once every tracker succeeded (skips don't count; user decision, 2026-10-18, which replaces "once at least one tracker succeeds" of 2026-10-02), the original in the watched folder is removed, file by file, only where this job put the seeding copy (same inode, another path: `_remember_seeded`, `_clear_watch_source`). While any tracker failed, the release stays where it was so Retry still has its files (event `watch_source_kept`, naming the trackers still missing), and the links made for the trackers that succeeded stay, since they seed. The retry that brings the last tracker to done removes it as a first full success would, counting the seeding copies of the trackers that succeeded in an earlier run too: each tracker's seeded files (device, inode, path) are also written to the job folder (`seeded-<target id>.json`, next to the published-id journal), since the files only those trackers seed (an nfo a reseed's torrent doesn't have) would otherwise stay behind as leftovers. The same record covers a restart or a resumed cancel; a tracker that runs again drops its old one, and a record that is missing or unreadable only keeps files. Before, any second link was enough, so a file already hardlinked elsewhere could be deleted while it was the one seeding. With "don't seed", or when nothing succeeded, it stays where it was. The copy is checked again right before the original goes (audit 2026-10-18): it must still exist as a regular file with the same inode at another path, and seed for a tracker that succeeded. The links made for an upload's names are removed when nothing seeds them, but never one that another tracker of the same job seeds: a reseed with the tracker's identical name reuses that very link, and removing it after a failed upload left the reseed without data and, from the watched folder, no copy of the release at all. Nor one that a torrent in the client index uses, or a reseed of the matching engine still running or approved after the links were made (the same name reuses the same inode): in doubt the link stays, at worst an orphan hardlink. Each link is checked again right before it goes (audit 2026-10-18): it must still be a regular file with the device and inode it had when the job made it, and it is removed through `nazgarr/library/hardlinks.py`, which never follows a symbolic link in the folders above; another file put in its place since (or a symbolic link) stays, in a warning event (`file_links_changed`). Before, the cleanup removed by path.
- **Rollback:** "Change match" (`back_to_match`) takes a job from the decision back to the match and redoes the analysis.
- **Incomplete seasons become episodes** (user decisions, 2026-10-09; setting `upload_watch_split_incomplete`, on by default; `nazgarr/upload/split.py`). A season pack with fewer episodes than its season has, in the numbering chosen at the match (e.g. the first 2 of 8 released together), is not uploaded as a pack but as one upload per episode, like episodes released one at a time. That holds even with a single episode missing.
  - **From the watched folder:** it happens on its own, right after the automatic match. Each episode gets the same trackers (and freeleech), match and episode ordering, goes through the analysis and stops at the decision as always. The pack's upload is closed (cancelled, listing the new ones, never resumed, no "upload finished" event).
  - **By hand:** at the match, an incomplete season pack offers "Split into N episodes". Hand-picked packs are never split.
  - **The count** (audit 2026-10-18): only the episodes the chosen season has count, so an E00 or an extra E13 doesn't cover a missing one. When an episode of the files doesn't translate into the chosen ordering, or two files land on the same episode while the season looks incomplete, the count is unknown: no automatic split (`split_skipped_untranslated`), it goes on as a season pack. Each episode is confirmed with the pack's orderings and its file's numbers translated as in the pack, never with orderings recomputed from its single file (which turned Part 2 S02E01 into S03E01).
  - **After a restart or a cancel** (audit 2026-10-18): the automatic match of a watched-folder pack writes `stage = split_pending` in the same update, cleared once the split has decided (each season of a split into seasons has it too, until its own split into episodes). The pack is closed and the split recorded in one commit. An upload created by a split whose pack was never closed is removed when the worker picks it up again, unless the pack is still in analysis: then the pack's analysis first removes those leftovers and, with `split_pending`, splits again from the start (an old wake-up for a reused id never touches the new uploads). Before, a restart in the middle analysed the pack whole next to the episodes or seasons already created, and a half-made season, holding the whole folder, split again. A cancel during a split leaves the pack cancelled, with no new uploads. "Split into N episodes" at the match works the same way (audit 2026-10-18): the split the user asked for is written with the match (`stage = split_requested`), so a restart in the middle splits again from the start, whatever the watched-folder setting; before, the leftovers were removed but the pack then went to the decision whole and the split asked for was silently dropped. A split by hand that fails clears it, and the pack goes on whole; one asked while a worker step is still working the pack (identification finishing its automatic match) is refused as busy (`upload_job_busy`, review of audit 2026-10-18 finding 155), since the analysis that follows would have split it a second time. The episode ordering chosen at the match is written in that same update too.
  - **All or nothing** (audit 2026-10-18): a split that fails halfway removes the uploads it already created, and the pack goes on whole; before, they stayed alive on the same files as the pack, and reached the decision next to it. The same holds for the split into seasons. A split by hand that fails, for any reason (a file that can't be read, a database error), answers with an error code and the pack goes on as a pack, never left waiting for a restart; if the split could not remove the uploads it created, the endpoint removes them (audit 2026-10-18).
  - **The leftovers:** once no episode to upload is left in the release's folder of the watched folder (the last one moved to the upload folder after seeding), the folder is removed with whatever is left (nfo, sample). A video still there (another episode not uploaded yet, or cancelled) or a file still being written keeps it. The check runs only once the episode's own upload is done on every tracker (2026-10-18): with a tracker failed, its video stays for Retry, and so does the folder. Only the files just checked are removed, then the empty folders (audit 2026-10-18): what can't be removed stays, listed in a warning event, and the upload stays done.

**The media folder is optional** (user decision, 2026-10-02): Nazgarr can also be used only to scan torrents and to upload releases, with no media folder at all. The storage step only needs the torrent folder. Without a library there is no health: the Dashboard says so instead of showing 100%, and scans store no health point, while the torrent numbers keep their trend.
- **Language check:** each tracker with a language gets a warning when no audio track (commentary excluded) is in that language.
- **Remux detection** (user decision, 2026-10-02): "VU" or "UNTOUCHED" in the name means REMUX, since guessit doesn't know them; so does a joined "BDRemux", "UHDRemux" or "DVDRemux" (common in Italian releases), which guessit only reads when separated, and it also gives the source. A disc source (BluRay, HD DVD, DVD) whose video carries no encoder trace (no x264/x265 writing library, no encoding settings) is a REMUX too, even if the name doesn't say so. A manual choice still wins.
- **Hybrid and remux source** (user decision, 2026-10-02): a REMUX whose Dolby Vision is profile 8 is HYBRID, since a pure remux has profile 7 or 5; so is a name that already says HYBRID. It is available as the `{hybrid}` variable and is editable in the detected details. At ITT a hybrid remux is "HYBRID REMUX", without VU (`hybrid_type_labels`). A REMUX with no source in its name is BluRay, or DVD at standard definition.
- **Disc source from MediaInfo** (user decision, 2026-10-05): when the name gives no source (a renamed file), MediaInfo can: the video's "Original source medium" (written by MakeMKV on every track it extracts, e.g. Blu-ray, HD DVD, DVD-Video) names the disc on its own; Dolby Vision profile 7 with an enhancement layer (UHD Blu-ray only) or VC-1 video say disc on their own; lossless audio (TrueHD, DTS-HD MA, LPCM) with PGS subtitles only when the video is also an encode or has a remux-level bitrate (40 Mb/s at 2160p, 18 at 1080p), since a DLMux/WEBMux takes audio and subtitles from a disc over web video. The source is then BluRay (DVD at standard definition), and the remux rule above applies, requiring the video itself to look like the disc's (DV dual layer, VC-1 or the bitrate). The release's `Movie name` tag is not used: encodes often keep their source's title. Why the type and source are what they are (`analysis.type_basis`) opens from the type tag in the detected details.
- **Web source from MediaInfo** (reported 2026-10-10): audio encoded by BAMTech (the encoder of Disney's streaming services: Disney+, Hulu, ESPN+), in an audio track's title or writing library or in an Audio section of the full MediaInfo, means a WEB-DL when the name gives no source. A WEBRip when the name says x264/x265: an encoder trace in the video alone is not enough, since some services leave it in genuine WEB-DLs. It is checked before the disc signals; a source in the name always wins (`naming.streaming_audio`).
- **Automatic rename** (setting `upload_auto_rename`, on by default): the default file names are those of the hardlinked torrent if there is one; otherwise the pattern is used for library files and watched-folder releases. Off: every upload starts with its original names, and each upload can still pick another option.
- **The season of the generated file names is the one chosen at the match** (user report, 2026-10-23: after re-matching a folder to another series and another season, the files kept the "S01" of their own names, while the release name already said S02). An episode in a folder takes the season and episode confirmed at the match, exactly as the release name; every video of a season pack takes the chosen season (episode numbers stay the files', translated by the chosen episode ordering); a complete pack keeps a file's season when it is among the chosen ones, otherwise, with the same number of seasons, they are paired in order (files S01, S02 chosen as S02, S03), its `Season NN/` subfolders included (`nazgarr/upload/file_names.py::season_mapping`). The tracker's season and episode fields already came from the match.
- **File names written by hand** (user request, 2026-10-16): with the generated names, the name of the torrent's file, or of a pack's folder, can be rewritten in the decision (override `content_name`; the file keeps its extension, a lone movie in a folder follows the folder, a pack's episodes keep their generated names). One name, not a path: `/`, `\`, control characters, `.` and `..` are refused. At most 200 characters and 240 bytes (audit 2026-10-18: filesystems count bytes, so a long name in accented letters failed only when the hardlink was made). A split into episodes or seasons does not copy it. The MediaInfo preview in the decision shows "Complete name" as the tracker will receive it, the path inside the torrent with the chosen names (`file_names.previews[mode].main_video`); execution already wrote that line (`nazgarr/upload/execute.py::refresh_mediainfo`).
- **Single file instead of a one-file folder** (user decision, 2026-10-02; setting `upload_single_file`, off by default): when the only file going into the torrent sits in a folder, the torrent is just that file. Samples and system files never enter the torrent, so they don't count; an nfo does. `upload_single_file_folder` decides where it seeds. `keep` (default) puts it inside its folder in the upload folder, with the client pointing there. `remove` puts it directly in the upload folder. A source already in the seeding folder (not from the watched folder) always seeds in place, inside its folder, with no new hardlink. In both modes the watched folder still empties as usual (`nazgarr/upload/file_names.py::_as_single_file`, `nazgarr/upload/execute.py::prepare_content`).
- **MakeMKV title suffix** (user report, 2026-10-03): MakeMKV names its files `Title_t00.mkv`, `_t01`, … (one per disc title). guessit reads the suffix as part of the title ("Title t00") or as the episode title, and the TMDB match goes wrong. Every guessit call on a local file name goes through `nazgarr/library/guess.py`, which strips `[_ ]tNN` at the end of the name first. That covers upload identification, the library resolver, Triage, torrent layout, packs and the naming detection.
- **Profile default for "internal"** (2026-10-03): `tracker_upload_profile.default_internal`, next to anonymous and personal release. It is the starting value of the flag on each upload, which can still change it.
- **Dolby Vision from the stream** (user decision, 2026-10-03): MediaInfo detects Dolby Vision only from the configuration record declared by the container (`dvcC`/`dvvC`). A file whose stream carries the RPU without that record shows up as plain HDR10/HDR10+ (MediaArea/MediaInfo #1312), so the name would lose `DV.Px` and HYBRID.
  - **The fallback** (`nazgarr/upload/dovi_probe.py`): when MediaInfo saw no Dolby Vision and the video can carry it (HEVC/AVC/AV1, 10 bit or more), ffprobe reads the first 16 packets. Reading only the first packet would miss MP4 files with B-frames. Any RPU found is added to the summary in MediaInfo's own form.
  - **The profile** comes from the configuration record when ffmpeg exposes it. Otherwise it is estimated from the RPU the way dovi_tool does: RPU profile 0 is 5; RPU profile 1 is 8 without residual and 7 with it. Anything else stays plain "DV".
  - **What the user sees:** the analysis logs a warning event. The text MediaInfo produces for the tracker is not changed.
  - **The image** ships both ffmpeg and ffprobe as static binaries, with no Debian ffmpeg and no system mediainfo, since pymediainfo bundles libmediainfo.
  - **Verified** with dovi_tool-generated P8.1 and P5 streams in MP4 and MKV without `dvcC`.
- **Packs picked by hand** (user decision, 2026-10-02): the user can make a season pack or a complete pack out of episodes downloaded one at a time. It works even when each episode already seeds with its own torrent, and even without a media folder.
  - **Picking:** "Pick for a pack" in the series sheet (library) and in the folder views (media and torrents). It shows checkboxes on the videos, plus one per season or per folder. Clicking "Create pack" opens the new upload with the list, passed in the navigation state.
  - **The source:** the job stores `pack_json` (`nazgarr/upload/pack.py`): the disk-relative files, each one checked again through `resolve_scoped` on every use, plus a name built from an episode name (`S01E01` → `S01`, `S01-S03` for a complete pack). There must be at least two videos, all on the same disk, with distinct file names and no symlinks. Subtitles next to an episode with its name are included automatically. `source_path` is only the files' common folder, and nothing ever walks it.
  - **The torrent:** it is always built from hardlinks: a new folder in the upload folder, with `Season NN/` subfolders for a complete pack. The episode torrents are left untouched. File names are generated by default, or the original names are kept inside the new folder.
  - **The analysis:** "already seeding here" now needs a client torrent that hardlinks every video, not just one. The name source for detection is the episode name turned into the season name.
  - **Mixed packs:** if resolution, video codec, HDR, audio codec, audio languages, source or group differ between the episodes, `analysis.pack_mixed` lists them. Uploads stay blocked until the user confirms (`pack_mixed_confirmed` override). Reseeds are not blocked.
- **Some seasons of a multi-season folder** (reported 2026-10-11: a whole series landed in the watched folder, and the S01 season pack carried every episode; `nazgarr/upload/pack.py::season_selection`). When the match confirms a season pack or a complete pack with only some of the seasons the folder has, the job becomes a pack of those seasons' videos, as if picked by hand. The episodes can sit in their own subfolder (`Season 01/`, where the season may come from the subfolder alone) or all together (`S01E01...`). Seasons are compared in the numbering chosen at the match.
  - **What stays out:** the other seasons, videos with no season in their name or folder, and anything that is not a video or its subtitles (nfo included), as in hand-picked packs. The event log says how many videos went in and how many stayed out.
  - **The name:** built from an episode name, as for hand-picked packs. When the episodes have no `S01E01` in their name, the folder name is used with the chosen seasons (`Show.S01-S03...` -> `Show.S03...`), and it also fills what the episode names don't say during detection.
  - **When the folder stays whole:** all of its seasons chosen (the automatic match always confirms them all), or none of them (the user renumbers: the files say S01, TMDB says S03).
  - **Back to the match:** "Change match" restores the whole folder (`from_folder` in `pack_json`), so another season can be chosen.
  - **Watched folder:** only the files this upload put in seed leave it; the other seasons stay there.
- **Several seasons become season packs** (user decision, 2026-10-11; setting `upload_watch_split_seasons`, on by default; `nazgarr/upload/split.py::split_seasons`). From the watched folder, right after the automatic match, a complete pack whose videos span at least two of the confirmed seasons becomes one upload per season. Each one is the same folder confirmed as that season's season pack, so it becomes a pack of that season's files (above).
  - **Like the episode split:** same trackers (and freeleech), match and episode ordering, reused without asking the sources again. The complete pack's upload is closed (cancelled, listing the new ones, never resumed). A season whose match can't be confirmed stays at the match with the whole folder.
  - **Then the episodes:** an incomplete season among them follows "Incomplete seasons become episodes" (its own setting).
  - **The leftovers:** once no video to upload is left in the folder, it goes with whatever is left, as for the episodes.
  - **By hand:** the complete pack stays one upload; choosing a season pack at the match takes only that season.

**Errors, caches and long lists in the web UI** (audit 2026-10-18):

- **Errors.** A render error or a chunk that no longer loads never blanks the app. An error boundary around the whole app and one around each page (it resets on navigation, so the menu, header and floating panels stay) show what happened, with Reload, Retry and, while viewing another instance, "Back to this instance". A chunk of a previous build that 404s after an upgrade reads as "a new version is available", and the view whose chunk failed (a page, or the whole app) reloads once (a `sessionStorage` flag prevents loops). A chunk that only decorates (the animated ring of the logo, which falls back to the still image) or a background preload that fails never reloads the page (audit 2026-10-18).
- **API errors.** `unwrap()` throws an `ApiError` with the HTTP status and the error code. Queries don't retry a 4xx (except 408 and 429), so a deleted upload shows its error at once. When `/api/auth/status` or `/api/auth/me` fails without a 401 (server down, proxy 502), the login gate says the server is not answering, with Retry, instead of offering account creation or a new login. Only a 401 asks to log in again.
- **Another instance's 401.** The browser drops this instance's token only for this instance's session codes (`auth_required`, `auth_setup_required`): never for the other instance's `api_key_invalid` through the proxy, nor for a local 401 that is not a session failure (a wrong current password when changing it, `auth_wrong_current_password`). An instance whose probe says its key is refused (`bad_key`) is blocked like an incompatible one, with the steps to replace the key.
- **Credentials that cannot be UTF-8** (audit 2026-10-18): a JSON lone surrogate (`"\ud800"`) passes the JSON parser and the request model, and encoding it raised an error: a 500 with a traceback in the log, from anyone, before the account existed. Now the setup code is just wrong (403, counted by the login limit), a username at login is just wrong (401 `auth_invalid_credentials`, counted), and a username or a new password at setup or at the password change is refused with 400 `auth_text_invalid`. A `NAZGARR_SETUP_CODE` whose bytes are not UTF-8 can never match, but no longer makes every setup a 500.
- **Silent failures.** Deletes, revocations, the webhook secret rotation, "log out everywhere" and the *arr webhook toggle show why they failed (`meta.toastErrors`, handled by the MutationCache). The other mutations already report their own errors.
- **Browser cache.** IndexedDB is written only when a persisted query has new data, never on every unrelated poll, plus once a day even if nothing changed, so a cache in daily use never reaches the 7-day expiry. It keeps the list views (library items, media and torrent files, duplicates, Triage) for the selected tracker filter only, plus the tracker filter setting itself, so the right variant draws at once; detail sheets are not kept. In memory, a list of a tracker filter no longer selected is dropped after the usual 5 minutes without a view, like any other query; only the selected one stays for the cache lifetime. The library lists stay fresh for 30 s, so switching views doesn't re-read them; invalidations and returning to the tab still refresh them.
- **Server cache** (audit 2026-10-18, `nazgarr/web/response_cache.py`). The heavy views (media and torrent files, library items, duplicates, the dashboard and, since the audit, Triage) are kept in memory per data version and answered with an ETag, a `304` when the browser already has that version. The version is a generation of the process that moves after every commit that wrote a table those views read, counted on every connection, so a change made in place outside a run (a file deleted or upgraded under the same name by a Radarr/Sonarr webhook, a title or poster filled in, a tracker's seed requirement edited) shows at once; before, a hand-kept summary of counts and maxima missed those until the next run. Tables written often that no cached view reads (upload progress, events and deliveries, queued webhooks, API key use, the TMDB search cache, file changes) don't move it; during a run the version is still a 15-second window. A body of a past version leaves memory as soon as the new one is computed, a computation that finishes after a newer commit is not kept (and never evicts the newer bodies), and at most 16 bodies and 64 MB stay. A tracker filter has one form per id (`01` is `1`), an id with no tracker counts as all trackers like any other unknown value, and a disk that doesn't exist is a `404`: every distinct value used to keep its own body of several MB until restart. Triage parses each file name for its quality once, not on every request.
- **Long lists.** Triage and the review queue render memoized rows in blocks as you scroll; the library tree renders memoized rows too, but only those in and near the visible part (windowing, §7). All three share one context menu, one "⋯" menu and one popover per list (Base UI detached triggers) instead of mounting them on every row. The poster grid starts again from the first block only when a filter or the search changes, not when the data refreshes in the background; the tree keeps the row at the top of the view where it was. In the tree a folder's name is a button that expands it (`aria-expanded`) and a file's name opens its detail sheet, so both work from the keyboard. Distances on screen are measured against the page's scrolling area, since the window itself never scrolls (measured against the window, every margin counted as zero); a sheet or a dialog uses the window. The next block of a long list is rendered when its end comes within 800 px of the visible part. A poster is downloaded when its card comes within 300 px and decoded off the main thread. In the library grid and the upload queue it is also released once the card is more than 1,500 px away, and fetched again (from the browser's HTTP cache) when it comes back: a grid scrolled to the end no longer keeps the image of every card it mounted. The poster in a detail sheet or an upload step stays once loaded. All images share one visibility observer per scrolling area and distance instead of one per card (audit 2026-10-18).
- **Background work.** The Logs tab reads the end of the log file, not the whole file on every 10-second poll. The scan status and the scan history ask for the last 10 runs (`GET /api/runs?limit=10`; without `limit` the API answers the last 100, `before_id` pages back), not every run ever made (audit 2026-10-18). The sidebar footer polls the dashboard every minute. Setup status is refreshed after a save only while the first-access tour is open or has never been seen. The 3D logo redraws its slow idle spin only when the inscription has moved by half a pixel, sizes its textures to the ring, frees its WebGL context on unmount, and shows the still image in the phone menu. Only the selected language's dictionary is downloaded.

**Install without Docker** (user decision, 2026-10-02): every release also ships a Python package, installable with pipx. It is a wheel with the web UI already built inside (`scripts/build_package.sh`). It is built for stable releases only, attached to the GitHub Release when a version is promoted (`promote-stable.yml`), and never for nightlies, so neither Docker nor Node is needed at runtime: only Python 3.12+, `mediainfo` and `ffmpeg`. The `nazgarr` command (`nazgarr/cli.py`) does what entrypoint and supervisord do in the container:

- `init` writes `config.yaml` and a Fernet secret key (0600) to the platform's config folder;
- `serve` always runs a single process;
- `install-service` writes a systemd user unit (Linux) or a launchd agent (macOS), and only prints the commands to enable it;
- `version`.

Without Docker there is no volume mapping: `disk_scan_root` is the real folder the disks are under. The package's dependencies are the ones in `requirements.in`, minus `supervisor`, and a test keeps them equal. Windows is not tested yet.

The package's dependencies stay unpinned (audit 2026-10-18): exact pins in the wheel would hold pipx users on old versions, security fixes included, until the next stable, and the lock is resolved for a single platform and Python 3.12. So the hash-locked `requirements.txt` protects Docker and CI only, and the pipx channel gets two things at each promotion instead. First, the built wheel is installed in a fresh venv with the newest dependencies, inside a throwaway container from the Python image of that version's Dockerfile: the installed package must start (`nazgarr version`, the app's import), and the version's own test suite runs from the source tree with those same dependencies. Only then is anything promoted, attached or published, so the set `pipx install nazgarr` receives is tested at release time. Second, the release carries `constraints.txt`, the lock's versions without `supervisor` and without hashes (a hash in a constraints file makes pip demand one for every package, nazgarr itself included, and the install fails), for a pinned install the README documents.

**Release pipeline** (audit 2026-10-18). `docker-publish.yml` calls `ci.yml` (ruff, pytest, oxlint, vitest, build) as a job and publishes nothing, nightly, test tags and branch builds included, unless it passes on the same commit. Before touching the registry, `promote-stable.yml` checks that the version is a plain X.Y.Z with its tag, that its commit is on `main`, that its GitHub Release exists and that the last `ci.yml` run on that commit succeeded: a test tag (`v0.9.1-dev`) or a hand-pushed tag can no longer move `:stable`. These checks run in a read-only job. Then the Python package is built and tested (above) before anything is promoted: if either fails, `:stable`, `:latest`, the GitHub Release and the `stable` tag all stay on the previous version, so the update check never tells pipx users about a version PyPI does not have. The package is built in a job with read-only access and no token, and the app's newest dependencies run only inside the throwaway container: some fifty packages just released on PyPI, with no lock or hash, never run on the runner itself, where they could reach the Actions token that writes the cache `docker-publish.yml` reads back for the images. A separate job that runs no repository code attaches the package to the release: on the package's path, that upload is the only step with write access. `npm ci` runs with `--ignore-scripts` everywhere. Dependabot waits 7 days before proposing a new pip or npm version (security updates excepted). Every external image of the Dockerfile, ffmpeg included, sits in a `FROM` line, the only one Dependabot reads, so its digest gets update proposals too. Still open: `build` and `setuptools`, which build the wheel, are fetched unpinned at promotion time and run on the runner; pinning them with hashes (a `requirements-build.in` compiled like the main lock, then `python -m build --no-isolation`) needs that lock compiled with network access.

### More instances in one web UI (user decisions, 2026-10-03)

One Nazgarr can open others: Configuration › Instances lists them (name, address, one of their API keys, encrypted at rest; `remote_instance`, `nazgarr/integrations/instances.py`).

- **Switching.** A switcher at the top of the sidebar changes the instance every view shows, and a banner always says which one it is. The choice lives in the browser and reloads the page, so caches, queries and the tour start clean. Each instance has its own browser cache.
- **The proxy.** The browser never talks to the other instance and never sees its key. Every call goes to this instance, which forwards it with the key (`/api/remote/{id}/…`), so no CORS is needed.
  - It forwards only `/api/…`, never login, API keys, instances or the proxy itself. The path is checked segment by segment and rebuilt from the checked segments (audit 2026-10-18): an empty, `.` or `..` segment, or a `%`, is refused, since `api/./auth/…` passed the old string check and httpx sent it as `/api/auth/…`.
  - It has timeouts and a size limit. The answer is read as it arrives and counted after decompression, which Nazgarr does itself in bounded steps (`nazgarr/core/http_limits.py`, only gzip and deflate announced): at most 64 MB in 120 s, otherwise `502 instance_response_too_large`. Before, httpx loaded and decompressed the whole answer before the check, so a few MB of gzip from a hostile instance filled the memory of the single process. The probe (`/api/health`, `/api/system/whoami`) reads at most 64 KB per answer.
  - A `401` from the other instance means its stored key is no longer valid there (revoked, rotated, mistyped): the proxy answers `502 instance_bad_key` and forgets the cached probe, so the next one shows the instance with a bad key. Passed through as it was, it looked like this instance's own session had expired.
  - It needs this instance's login: an API key of this instance cannot use the keys of the others.
  - In the browser, the API client sends a call of another instance to the proxy as a new request built from the original one's method, headers, signal and body, the body read in full first (`frontend/src/api/client.ts`, audit 2026-10-18). Before, `new Request(url, request)` relied on the browser copying the original request's properties, and turned the body into a stream, which Chrome sends only with `duplex` over HTTP/2 and Firefox and Safari do not send at all; in the tests' runtime the copy came out as a GET with no headers and no body.
- **Reaching an instance.** LAN or VPN addresses (private, CGNAT/Tailscale) are allowed over `http://`. A public address only over `https://`, so the key never travels in clear. To open a home instance from a VPS, use a VPN such as Tailscale or WireGuard.
- **Versions.** The UI speaks the API of its own version, so it compares major.minor with each instance:
  - the other instance is older by a minor: a warning;
  - a different major, or the other instance is newer: blocked, both in the UI and in the proxy, until they match.
  - **The same minor with fewer endpoints** (audit 2026-10-18): the patch versions of one minor can add endpoints, and an older 0.9.x reads as compatible. Two pages call new ones as they open: the upload history (`GET /api/uploads/history`) and the review queue in pages (`GET /api/reviews/queue`). An older remote answers them 404, 405 or 422 through the proxy, and the upload page became the error ring (the active queue too) while the review queue said "No pending reviews". The API client answers such a call to another instance with the endpoint that instance has (`frontend/src/api/compat.ts`): every finished upload from `GET /api/uploads`, or the whole queue from `GET /api/reviews`, as a single page. On this instance a missing endpoint stays an error. The pages themselves no longer hide a failure: a history that does not load says so in its tab, with Retry, and leaves the active queue usable; the review queue says "No pending reviews" only once it was read, and shows a failed load (a 5xx, the network down) as an error with Retry.
- **What the key decides.** A read-only key only looks. Secrets, safety settings and API keys stay with that instance's own interface: an API key cannot change them. Security and API keys are hidden while on a remote, and every settings page says so.
- **Overview.** `/instances` shows every instance with its library health, reviews waiting, uploads in progress and last scan.
- **Command line.** `nazgarr instance ls/add/test/rm` manages the list, and asks for the password.
- **Key level.** The test of an instance reads its version and, through `GET /api/system/whoami` (added for this), whether the key is read or write.

- **Access:**

  - `nazgarr setup` creates the account of a fresh install with the one-time code.

  - Secret settings and safety settings, which an API key may not change, ask for the password and log in for that single change.

### HTTP, login and permissions hardening (audit 2026-10-18)

The mandatory login (user decision, 2026-10-01) and the rules above are unchanged. What changed around them:

- **Request size.** Every request body is capped at 2 MB by a pure ASGI middleware, the outermost layer (`nazgarr/web/body_limit.py`): a larger `Content-Length` gets `413` without being read, and a chunked body is counted as it arrives. No route takes files, so no legitimate body comes close. FastAPI decodes the body before it checks the login, and even under 2 MB a crafted JSON cost over 100 MB and most of a second of the event loop per request, so outside `/api/auth/*` no body byte reaches the app before the credentials are checked (the same check as the route, giving its `401`/`403`). `/api/auth/*` bodies, which must work without a login, are capped at 16 KB. The Radarr/Sonarr webhook keeps its own 1 MB cap, read only after the webhook password. A `422` lists type, position and message of each error (at most 50), never the rejected input.
- **Which routes are open.** Without credentials only `GET /api/auth/status`, `POST /api/auth/setup`, `POST /api/auth/login`, `GET /api/health` and the webhook endpoint (with its own password) answer. A test calls every operation in the OpenAPI schema anonymously and expects `401` (`tests/test_route_auth.py`). `/api/health` gives version and commit only to a valid token or API key; anonymous callers, such as the container's healthcheck, get only the status. `/docs` and `/redoc` are gone (the app's CSP blocked their CDN scripts, so they were blank pages); the schema stays at `/openapi.json`.
- **What an API key can't do.** Besides managing keys, instances and the proxy, no key can change the password or log out every device: both need the login.
- **Login attempts.** Still 5 failures in 15 minutes per address, but the attempt is reserved before the password is checked, so attempts sent together can't all slip through; a success clears the count. Wrong current passwords in the password change have their own count and don't block the login. Behind a reverse proxy, `FORWARDED_ALLOW_IPS` (README) gives each visitor its own count.
- **Password and tokens.** PBKDF2-SHA256 with 600,000 iterations; a weaker stored hash is redone at the next successful login. Tokens carry `aud`, a random id of the installation, and must have `exp` and `sub`; tokens issued before this change, without `aud`, stay valid until they expire (at most 30 days after the first start with it).
- **Service addresses.** The DNS part of `net_guard` for tracker, client and Radarr/Sonarr URLs runs in the endpoint (threadpool), not in the request validator, which runs on the event loop. Moving a service from `https://` to `http://` on the same host counts as a new host: its secrets must be sent again (with its own error, `secret_required_for_insecure_scheme`, since the host did not change) and the RSS key is forgotten. The same rule holds for every `url` field of a plugin's settings, enforced once in `nazgarr/plugins/config.py::validate`: notification services (also the test of a saved service with other values), global plugin adapters (image hosts, resolvers) and plugin fields on tracker and client rows. Before, a write API key could point the server of a plugin like the ntfy example at its own host and receive the stored token at the first test.
- **The connection goes to the address that was checked** (audit 2026-10-18, `nazgarr/core/net_guard.py`). `check_url` resolves a name before each request, but httpx then resolved it again on its own to connect, so a DNS answer that changed in between (DNS rebinding) could take a request that had passed the check to the cloud metadata. The clients built for URLs that come from users or trackers (`net_guard.http_client`: tracker adapter, its download links included, Radarr/Sonarr and their connection test, other Nazgarr instances, webhooks and their test, tracker icons) resolve the name once, when the connection opens, refuse it if any address is forbidden (a connection error, handled like an unreachable host) and connect the socket to the address that was checked. Host header, TLS SNI and certificate verification stay on the name in the URL. A request through a proxy (`HTTPS_PROXY` and the like) is resolved by the proxy, so the pinned client itself checks the URL's host before each such request, with the same connection error (revision of the audit 2026-10-18: before, only the callers that ran `check_url` before every request did, and Radarr/Sonarr, the other instances and the client adapters did not). The torrent client adapters built on httpx (Deluge, qui, its instance list included, Transmission, rTorrent) are pinned the same way (audit 2026-10-18), with the LAN, where clients live, still reachable as before. qBittorrent goes through `qbittorrent-api`, on `requests`: its address is checked again whenever its adapter is built (once per operation), for a clear error, and every `requests` session the library builds (again after it picks the scheme) connects through `net_guard.requests_adapter`, which resolves the name once when the connection opens, refuses a forbidden address and connects the socket to the checked one, TLS staying on the name, and checks the host before a request through a proxy (revision of the audit 2026-10-18; before, the gap between the check and `requests`' own lookup stayed). The Discord and Telegram notifications are pinned too (audit 2026-10-18, since 2026-10-21): their hosts are fixed (`discord.com`, `api.telegram.org`), but their name resolves through the same DNS as every other, so they now take the same client instead of a plain one after `check_url`.
- **Plain http:// to a public host** (user decision, 2026-10-18). A tracker, torrent client or Radarr/Sonarr instance whose address is `http://` to a public host is saved, not refused (unlike another Nazgarr instance, above), with a visible warning: its token, password or API key travel in clear. The API computes it on every tracker, client and instance (`insecure_public_url`, `nazgarr/api/types.py`) with the same rule as the instances (`is_public`: LAN, loopback and 100.64.0.0/10 are not public, a name that does not resolve is; each host's verdict is kept 10 minutes, that of a name that does not resolve only 30 seconds, so a LAN container briefly missing from DNS does not show the warning for long). Settings shows it on the service's card and under the address in its form (while typing, an estimate from the address itself: private IPs, a one-word name, `.lan`, `.local`, `.home.arpa`, `.internal`, `.ts.net`; the server's verdict while the address is the saved one), and the CLI prints it on stderr after `add`, `edit` and `config import`. Never for a tracker's announce URL, which Nazgarr only writes into the torrents it creates.
- **Browser cache.** `index.html` is always revalidated (`no-cache`); the content-hashed files under `/assets` are cached for a year (`immutable`).
- **File permissions.** No process-wide `umask 077` any more: the data folder is `0700` and the database `0600` at every start, and the container's umask comes from `UMASK` (default `022`). Folders Nazgarr creates on the disks (`hardlinks.make_dirs`: seeding folders of reseeds and uploads, folders made from the disk browser) get at least the permissions, and the group, of the folder they are created in, so a torrent client running as another user of the same group can enter them. Permissions are only ever added, and Nazgarr always keeps `rwx` on its own folders; under a parent whose mode bits are all zero (an ACL-managed share, e.g. Synology or a TrueNAS NFSv4 dataset) the mode is left to the inherited ACL.
- **Logs.** uvicorn's access log goes through the same redaction as the rest (a `?token=` webhook password no longer appears in clear). The line httpx writes for every request keeps only method, scheme, host and port of the URL, and the status: the path carried the Telegram bot token (`/bot<token>/sendMessage`) and the Discord webhook token at every notification, readable by a read-only API key in `GET /api/system/logs`. The redaction also covers those two paths and the credentials inside a URL (`https://user:password@host`, a token alone as in `git+https://<token>@github.com/...`), in the logs, in the error texts saved in the database (now also a run's list of errors, `errors_json`, which the scan history shows, and the `detail` of webhook events and not-imported torrents; a test checks every `*_error`/`*_detail` column) and in `GET /api/plugins` (the plugin list and its install error). `GET /api/system/logs` redacts every line again as it reads it, tracebacks included, since lines written before these patterns stay in `nazgarr.log` until it rotates. A `*_json` column (`errors_json`, `params_json`) is redacted value by value, not as text: the text patterns ate the backslash of an escaped quote, the JSON no longer parsed and the scan history lost the run's list of errors.
- **Settings.** `PUT /api/settings/{key}` refuses, to everyone, the keys that have their own endpoint or are internal state (`setting_protected`, `settings_registry.MANAGED_KEYS`): `schedule_cron` and the last scheduled slot, the `APP_SECRET_KEY` canary, the plugin switch, the file naming rules of uploads, the instance name, the update check and release notes state, the not-imported status and the identity rules version. Written from there they skipped their own checks: a bad cron stopped the next start, and only an edit of the SQLite file brought the app back. They can still be read. **Only registered keys** (audit 2026-10-18): every other key is refused, read or written, with `400 setting_unknown`. Before, the generic endpoint saved any key with any value, so the protection was a list of exclusions, and a new internal-state key of a module was writable through it until someone remembered to add it to `MANAGED_KEYS`. Free text has its own kind in the registry (`text`, with a maximum length: 100,000 characters for the exclusion patterns and the description header and signature, less for the rest): the TMDB and TVDB keys, the exclusions and their presets, the releaser name, the image host order, and the interface's own state (time zone and formats, size units, the library's default view, the tracker filter, the first-access tour, the dismissed notice of the removed image hosts). A test reads the keys the interface uses from its sources and fails on one that is not registered. The CLI lists every registered key except the interface's own state (`settings ls`, `config export`), and `nazgarr settings set` leaves an unlisted key to the server, which refuses it unless it is one of those; `config import` reads each setting's current value while it builds its plan, so a key that is not a setting stops the whole file before any change. Only the value of a secret key is ever decrypted (an `enc:` value on any other key broke every read of it), and a new secret is always encrypted, also when it starts with `enc:`. A secret setting (the TMDB and TVDB keys) is write-only like the secrets of trackers, clients and plugins: `GET` and `PUT` answer `value: null` with `is_set`, and the Metadata page shows that a key is saved, with Save enabled only once a new one is typed and a Remove button (with confirmation) to clear it. Before, every browser session read them back in clear; `nazgarr settings get` now says only `(set)` or `(not set)`. The CLI refuses those keys in `settings set` and `config import` and says where they are changed.
- **Error answers.** Every error the API returns is `{code, params}` (`nazgarr/core/errors.py`), translated by the UI and the CLI; the last free-text ones (a review already being verified, a full hash check not found or that cannot start, an execution that cannot be deleted because it is seeding: `seed_job_not_deletable`) are codes too, and a test fails on a literal, `str(exc)` or `safe_error(exc)` detail under `nazgarr/api` (the retry of a failed execution is the one allowed exception). An execution that fails or cannot be retried still answers with its English text, redacted.

## 11. Tech stack

Inherits ratio-guardian (CLAUDE.md), with additions for multi-client and posters:

- **Python 3.12**, **FastAPI** (pure JSON API under `/api/*`)
- **SQLite** via SQLAlchemy — enough for this load. Every connection (`nazgarr/core/db.py::_configure_sqlite`) turns on foreign keys and WAL, with a 30 s busy timeout. `synchronous` stays at SQLite's default, FULL: with NORMAL a power cut can lose the last commits, and the upload worker relies on the one that marks a target `uploading` before the tracker call to never upload the same torrent twice. Since the audit of 2026-10-18 every connection also gets a 16 MiB page cache, and from SQLite 3.46 it runs `PRAGMA optimize` when it opens, so the query planner has statistics; the pool reopens connections every 6 hours, and the optimize is skipped when another writer holds the lock. On an older SQLite (the pipx package uses the system's, 3.45 on Ubuntu 24.04) that PRAGMA sees no table on a new connection, so an `ANALYZE` runs at every start instead.
- **APScheduler** in-process for scheduling
- **httpx** for tracker/TMDB calls (async-friendly)
- **qbittorrent-api**; Deluge, Transmission and rTorrent/ruTorrent through their own APIs with httpx and the standard `xmlrpc.client`, no extra library (section 5)
- **pymediainfo** for mediainfo/Unique ID
- **guessit** for filename parsing
- **torf** to create `.torrent` files for uploads (pure Python)
- **ffmpeg-python** for upload screenshots (needs `ffmpeg` in the container)
- A minimal BEP3 bencode parser (ratio-guardian's `app/torrent_file.py`, ported as `nazgarr/torrents/metainfo.py`) — used both for the folder-name fallback (ratio-guardian §7: `info.name` of a multi-file torrent, applied by `full_check._sync_folder` and the matching) and for the piece hash (section 6). A `.torrent` comes from a tracker, so every field is checked (audit 2026-10-18): types, no negative length, a piece length up to 256 MiB, exactly one hash per piece of the content; anything else is a `TorrentMetainfoError`, never a crash or partial data. Piece hashes (the matching sample, the full check, the upload dupe check) are computed in reads of at most 4 MiB, so memory never depends on the piece length the tracker declared.
- **Frontend**: **React + shadcn/ui** SPA, Vite build, served by the FastAPI container
- **Single container with supervisord**, which runs one process: the FastAPI app, with APScheduler and the upload worker inside it (same pattern as ratio-guardian)

## 13. Open source requirements

- No personal data (paths, trackers, user credentials) in any versioned file — `config.example.yaml`/`.env.example` with generic placeholders.
- An explicit LICENSE (still to choose — MIT/AGPL are the typical picks for this kind of self-hosted tool, AGPL if the goal is discouraging closed-SaaS forks).
- Bundled tracker profiles (section 9) contain only publicly verifiable mapping/naming, never credentials.
- Setup documentation (README) good enough for a third-party user with no context from the design sessions — never assume the reader knows ratio-guardian or the other source projects.

## 14. Suggested roadmap

1. Bootstrap the project (stack, folder structure, requirements) — reusing ratio-guardian's structure/config as a reference.
2. DB schema (disks/media paths/torrent index/tracker/client/media_item with poster/candidate/match_review/seed_job) + SQLAlchemy models.
3. Scoped-per-disk file browser API (a pattern reusable as-is from ratio-guardian).
4. Torrent client adapters: qBittorrent first (direct reuse), then Deluge/Transmission/rutorrent/qui by the priority in section 5.
5. Media resolver (guessit + TMDB) + poster download/cache.
6. Matching engine (size + mediainfo + piece hash) for both directions (section 3), explicit confidence.
7. Review queue UI.
8. Executor: hardlink + add-to-client + forced recheck, both directions.
9. Library view (tree + grid) built on the unified state.
10. Scheduler + run history.
11. Upload module (torf, mediainfo/screenshots, tracker profiles, dupe-check, human confirmation).
12. Cleanup for open source release (example config, LICENSE, README).

Not binding to the letter, but respects the logical dependencies (e.g. there's no point building the Library view before a unified state exists to show).
